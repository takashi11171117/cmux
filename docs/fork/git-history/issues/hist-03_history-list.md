## 🎯 目的

履歴タブにコミットを新しい順に並べ、スクロールで継ぎ足す。

**依存: HIST 01（器）と HIST 02（データ）の両方が閉じていること。**

## ✅ やること

- [ ] `GitHistoryStore`（ページ連結・SHA での重複排除・末尾判定）
- [ ] `GitHistoryPanelView`（短縮ハッシュ・件名・作者・相対日時）
- [ ] 末尾に近づいたら次ページを読む
- [ ] HEAD 署名の変化で先頭ページを読み直す
- [ ] リポジトリ根は `FileExplorerStore.rootPath` +
      `GroupDirectoryFallback`（Git タブと同じ）
- [ ] git 管理外・初コミット前で「履歴なし」
- [ ] ローカライズ（相対日時を含む）
- [ ] テスト

## ⚠️ 落とし穴

**行より下に observable を置かない。`body` から状態を書かない。**
どちらも upstream #2586 の 100% CPU スピンループの再発条件
`[CLAUDE.md「SwiftUI list boundaries」]`。`GitChangeTreeRow` と同じく
平坦化した行を1本の `ForEach` に流す。

**ページ継ぎ足しは `onAppear` から呼ぶ。** `body` からは呼ばない。

**重複排除は SHA で。** ページ境界でコミットが増えると `--skip` がずれ、同じ
コミットが2度来る。

**末尾判定は「返ってきた件数 < 要求件数」。** 空が返るまで問い続けると、履歴の
最後で無駄な `git log` を回し続ける。

**行の高さは固定。** 可変にするとスクロール量の計算が狂う。

## 📐 実測で決めること

- 初回に読む件数
- どこまでスクロールしたら次を読むか

机上では決められない（`git log` の所要時間がリポジトリ規模に依存する）。
cmux 本体のような数万コミットのリポジトリで測って決める。決めた値と根拠を
`docs/fork/git-history/02_要件定義.md §5` に書き戻す。

## 🧪 完了条件

- コミットが新しい順に並ぶ
- 下までスクロールすると継ぎ足され、位置が飛ばない
- 別ターミナルで `git commit` すると数秒以内に先頭に現れる
- ファイルを保存しただけでは読み直さない
- ブランチを切り替えるとその履歴に入れ替わる
- Git タブと History タブが常に同じリポジトリを指す
- 数万コミットのリポジトリで、開いた瞬間に固まらない
