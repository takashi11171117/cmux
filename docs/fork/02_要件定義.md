## 0. 実装前に決める最上位事項（依存する FR に明記）

**Panel 層に足すか Surface 層に足すか**（REQ-19 / 未確定-01）が未決である。この決定は FR-01 / FR-05 / FR-07 / FR-10 の形を変える。各 FR にその旨を明記した。

本書作成時の実コード確認で、01 §6 訂正の前提のうち一部が実態と異なることが判明した。未確定-01 の判断材料として先に記す。

- `CmuxSurfaceType`（`terminal` / `browser` / `project` の3種）は **cmux 設定ファイルの宣言的レイアウトスキーマ**であり、`CmuxPaneDefinition.surfaces` の要素型 `[実装済み: Sources/CmuxConfig.swift:1589-1590, 1610-1624]`。リポジトリ内の参照は `Sources/CmuxConfig.swift` の2箇所のみ（`grep -rn "CmuxSurfaceType" --include="*.swift" .` の結果が 1611 行目と 1620 行目だけ）。
- **Session Restore の永続化単位は `CmuxSurfaceType` ではなく `SessionPanelSnapshot`** で、種別は `PanelType` が持つ `[実装済み: Sources/SessionPersistence.swift:1689-1719, Sources/Panels/Panel.swift:6-21]`。`PanelType` は既に **15種**ある（`terminal` / `browser` / `markdown` / `filePreview` / `rightSidebarTool` / `customSidebar` / `simulator` / `agentSession` / `project` / `extensionBrowser` / `workspaceTodo` / `notifications` / `cloudVMLoading` / `mobilePairing` / `accountSignIn`）。
- したがって 01 §6 訂正の初版にあった「Surface が Session Restore の永続化単位」という記述は、実コードと一致しない。`CmuxSurfaceType` に種別を足すかどうかは **設定ファイルから宣言的にエディタを開けるようにするか**の話であり、Session Restore の可否とは別軸。`[実装済み: 上記2点]`
  - **2026-08-17 追記**: この指摘を受けて 01 §6 の訂正ブロック本体を差し替え済み。01 側の記述と本書は現在一致している。

## 機能要件（FR-xx）

### FR-01 テキストエディタのシンタックスハイライト表示

**内容**: 既存 `FilePreviewTextEditor` が表示するテキストに、拡張子から判定した言語のシンタックスハイライトを適用する。新規エディタは作らない。`[メモ由来: §0 結論1, §4 訂正]`

**土台（既存）**: TextKit 1 を明示構築した `NSTextView` サブクラス `SavingTextView` が `NSTextStorage` / `NSLayoutManager` / `NSTextContainer` を保持している `[実装済み: Sources/Panels/FilePreviewTextEditor.swift:143-186]`。ハイライトは `NSTextStorage` の属性付与として載せられる。テーマ配色の適用点は既存の `applyTheme(to:backgroundColor:foregroundColor:drawsBackground:)` `[実装済み: 同 95-112]`。

**未実装であることの確認**: `grep -rni "syntaxhighlight|SyntaxHighlighter|treesitter|tree-sitter|textmate|Highlightr|Splash" --include="*.swift" Sources/` は macOS アプリ本体 `Sources/` で 0 件。`[実装済み: 該当なし＝未実装]`

**依存**: 未確定-01（Panel 層 / Surface 層）。Panel 層に足す場合は `FilePreviewTextEditor` と `SavingTextView` の変更で閉じる。Surface 層に独立させる場合は `CmuxSurfaceType` と設定スキーマの変更が加わる。

**受け入れ条件**
1. `.swift` ファイルを File Preview で開くと、キーワード・文字列・コメントが本文色（`themeForegroundColor`）と異なる色で描画される。
2. ハイライトが有効な状態でも、編集・Undo・Redo・保存が FR 追加前と同じ結果になる（NFR-06 の回帰テストで確認）。
3. ハイライト適用処理がメインスレッドをブロックしない（NFR-04）。
4. ライトテーマ / ダークテーマの両方で、背景色に対して本文が判読できる配色になる（FR-11）。

### FR-02 言語判定と非対応時のフォールバック

**内容**: ハイライト対象の言語はファイル拡張子から決定する。判定できない拡張子ではハイライトを適用せず、既存どおりのプレーン表示で編集可能とする。`[メモ由来: §14]`

**対応言語の最低ライン**: Swift / TypeScript / JavaScript / Dart / PHP / Python / JSON / YAML / Markdown / C / C++ / Rust / Go `[メモ由来: §14 → REQ-08]`

**リポジトリ内の先例**: iOS 側に拡張子→言語の対応表が既にある `[実装済み: Packages/iOS/CmuxAgentChatUI/Sources/CmuxAgentChatUI/Artifacts/ChatArtifactSyntaxHighlightPolicy.swift:8-64]`。この表は REQ-08 が求める13言語すべて（`swift` / `ts`,`tsx` / `js`,`jsx`,`mjs`,`cjs` / `dart` / `php` / `py` / `json` / `yaml`,`yml` / `md`,`markdown` / `c`,`h` / `cpp`,`cc`,`cxx`,`hpp`,`hh` / `rs` / `go`）を含む。判定不能時の挙動も定義済み `[実装済み: 同 67-85]`。

**受け入れ条件**
1. 上記13言語の代表拡張子を開くと、いずれもハイライトが適用される。
2. 拡張子なしのファイル、および対応表にない拡張子（例 `.foo`）を開くと、ハイライトは適用されず、テキストは欠落せずそのまま表示・編集できる。
3. 言語判定はファイル内容のスニッフィングに依存せず、拡張子のみで決まる。

### FR-03 ハイライトのサイズ上限とスキップ

**内容**: 一定サイズを超えるファイルはハイライトを行わず、プレーン表示にフォールバックする。ファイル自体は既存の上限まで開ける。`[メモ由来: §36, §37]`

**既存の上限**: テキスト読み込みは 16 MB を超えると `.unavailable` を返す `[実装済み: Sources/Panels/FilePreviewPanel.swift:906, 922-926]`。この上限は変更しない（NFR-05）。

**ハイライト側の閾値**: iOS 側は「ハイライト上限 1,500,000 バイト / 言語自動検出上限 256,000 バイト」を採用済み `[実装済み: Packages/iOS/CmuxAgentChatUI/Sources/CmuxAgentChatUI/Artifacts/ChatArtifactSyntaxHighlightPolicy.swift:5-6]`。macOS 側で同じ値を使うかは `[提案]`（未確定-05）。

**受け入れ条件**
1. 閾値超過のテキストファイルを開くと、ハイライトなしで全文が表示され、編集・保存ができる。
2. 閾値超過時にハイライトライブラリの処理が起動しない（起動しないことをテストで確認できる形にする）。
3. 16 MB を超えるファイルは FR 追加前と同じく `isFileUnavailable` 扱いになる（NFR-05）。

### FR-05 行番号表示

**内容**: エディタの左端に行番号を表示する。`[メモ由来: §4 訂正, §13 訂正]`

**未実装であることの確認**: `grep -rni "NSRulerView|lineNumberView" --include="*.swift" Sources/` は 0 件。`lineNumber` を含むヒットは File Explorer の検索結果（`Sources/FileExplorerSearchController.swift:7,22,32`）と設定ソース表示（`Sources/Settings/ConfigSource.swift:298,324,334`）のみで、エディタの行番号ではない。`[実装済み: 該当なし＝未実装]`

**土台（既存）**: エディタは `NSScrollView` の `documentView` として構成されており、`NSScrollView` の縦ルーラー領域を使える `[実装済み: Sources/Panels/FilePreviewTextEditor.swift:31-56]`。行の折り返しは `fileEditor.wordWrap` によって切り替わる `[実装済み: 同 194-218]`。フォントサイズはピンチ・スクロール・ショートカットで動的に変わる `[実装済み: 同 293-343, 403-413]`。

**依存**: 未確定-01（Panel 層 / Surface 層）。

**受け入れ条件**
1. テキストファイルを開くと左端に 1 始まりの行番号が表示され、本文の各行と縦位置が一致する。
2. `fileEditor.wordWrap` が true で行が折り返された場合、折り返し後の各表示行ではなく論理行に対して1つの番号が表示される。
3. フォントサイズをピンチ/⌘+/⌘- で変更しても、行番号と本文の縦位置が一致し続ける。
4. スクロールしても行番号が本文に追従する。
5. 行番号の桁が増えても（1 → 10000）本文が水平に切れない。

### FR-07 外部変更 × 未保存バッファの選択 UI

**内容**: 未保存の編集がある状態でファイルが外部から変更されたとき、Reload / Compare / Keep Mine を選ばせる。`[メモ由来: §35 + 訂正 → REQ-09]`

**土台（既存・検知機構は実装済み）**
- ファイル監視: `FileWatcher` がパスの変更イベントを流し、変更ごとに再読込を走らせる `[実装済み: Sources/Panels/MarkdownPanel.swift:429-443, Sources/Panels/FilePreviewPanel.swift:997-999]`。
- 未保存判定: `isDirty` を保持 `[実装済み: Sources/Panels/FilePreviewPanel.swift:985, Sources/Panels/MarkdownPanel.swift:34]`。
- **現状の衝突時の挙動**: 未保存バッファは破棄されない。外部変更を検知して再読込したとき `isDirty` なら `originalTextContent`（＝ディスク側の内容）だけを差し替え、ユーザーの `textContent` は温存し、`isDirty` を再計算するだけで **ユーザーに何も提示しない** `[実装済み: Sources/Panels/FilePreviewPanel.swift:1193-1196, 1286-1292, Sources/Panels/MarkdownPanel.swift:373-378]`。

**残作業**: 上記の暗黙 Keep Mine を、ユーザーが3択から選べる形にすること。検知機構の新規実装は不要。

**依存**: 未確定-01（Panel 層 / Surface 層）。`FilePreviewPanel` と `MarkdownPanel` の両方が `FilePreviewTextEditingPanel` を実装しており `[実装済み: Sources/Panels/FilePreviewPanel.swift:974-975, Sources/Panels/MarkdownPanel.swift:16]`、選択 UI は両方に効く必要がある。

**受け入れ条件**
1. 未保存の編集がある状態でファイルを外部から書き換えると、Reload / Compare / Keep Mine の3択が提示される。
2. Reload を選ぶと、エディタの内容がディスクの内容に置き換わり、`isDirty` が false になる。
3. Keep Mine を選ぶと、エディタの内容が変わらず、`isDirty` が true のまま維持され、その後の保存でディスク側が上書きされる。
4. 未保存の編集が **ない**（`isDirty == false`）状態での外部変更は、選択を出さず従来どおり自動再読込する。
5. 選択を出している間にさらに外部変更が起きても、ユーザーのバッファが失われない。
6. Compare の挙動は FR-08 で定義する。

### FR-09 外部エディタへの行番号受け渡し

**内容**: 「このアプリで開く」から外部エディタを起動する際に、ファイルパスに加えて現在のカーソル行を渡す。`[メモ由来: §25 訂正 → REQ-11]`

**土台（既存）**: 外部アプリでの「開く」は実装済み。`FileExternalOpenApplicationResolver.live.applications(for:)` が候補アプリを列挙し、既定アプリの「Open in <App>」と「Open With」サブメニューを構築する `[実装済み: Sources/FileExplorerExternalOpenMenuItems.swift:4-50]`。受け渡しているのは `FileExplorerExternalOpenRequest(fileURL:applicationURL:)` の2値のみで、行番号は含まれない `[実装済み: 同 22-25]`。

**残作業**: 行番号を渡す経路の追加。

**状態**: 受け渡し形式が未決 `[要確認]`（未確定-04）。LaunchServices 経由のアプリ起動には行番号を渡す口がなく、VS Code の `code --goto <file>:<line>` / Cursor / Xcode でそれぞれ引数形式が違う。既存の起動経路（アプリ URL を指定した LaunchServices 起動）を維持したまま行番号を渡せるかを確認する必要がある。

**受け入れ条件**: 未確定-04 の決定後に確定する。少なくとも次を満たすこと。
1. 行番号を渡せないアプリを選んだ場合でも、従来どおりファイルが開く（回帰しない）。
2. 対応アプリでは、指定した行にカーソルが立った状態で開く。

### FR-10 拡張子から表示先へのルーティング拡張

**内容**: ファイルを開く経路を一箇所に集約し、拡張子で Markdown / 画像 / コードの表示先を振り分ける。**新規ルーターの作成ではなく既存ルーターの拡張**として行う。`[メモ由来: §7, §8 訂正 → REQ-10]`

**土台（既存）**
- 集約点: `CommandClickFileOpenRouter` が `shouldRouteInCmux(path:)` → `openInCmux(workspace:sourcePanelId:filePath:)` の順で判定し、Ghostty 側のデッドロック回避のため `deferredOpenFileInCmux(...)` で次のランループへ遅延させる `[実装済み: Sources/CommandClickFileOpenRouter.swift:5-107]`。
- 振り分け: Markdown 拡張子（`md` / `markdown` / `mkd` / `mdx`）は Markdown へ、それ以外の通常ファイルは File Preview へ `[実装済み: Packages/macOS/CmuxSettings/Sources/CmuxSettings/Stores/FileRouteSettingsStore.swift:82-101, Sources/CommandClickFileOpenRouter.swift:22-41]`。
- 表示先の生成: `Workspace.openOrFocusMarkdownSplit(from:filePath:)` / `Workspace.openOrFocusFilePreviewSplit(from:filePath:)`。同じパスの既存パネルがあれば新規作成せずフォーカスする `[実装済み: Sources/Workspace.swift:8837, 9111-9135]`。
- File Preview 内の表示モード分岐: `text` / `pdf` / `image` / `media` / `quickLook` を `FilePreviewKindResolver` が解決 `[実装済み: Sources/Panels/FilePreviewPanel.swift:643-655]`。
- File Explorer のダブルクリック動作: `preview`（内蔵プレビュー） / `defaultEditor` / `preferredEditor` の3分岐で、**既定は `preview`**（内蔵プレビュー） `[実装済み: Sources/FileExplorerDoubleClickActionSettings.swift:9-19, 33, 69-81]`。

> 01 §8 訂正の「現状は外部アプリ起動に倒れている」という記述は、既定値 `.preview` と一致しない `[実装済み: Sources/FileExplorerDoubleClickActionSettings.swift:33]`。既定では内蔵プレビューに倒れる。

**残作業**: 01 §7 が挙げるコード拡張子（`.swift` / `.ts` / `.tsx` / `.js` / `.dart` / `.php` / `.py` / `.rs` / `.go` / `.cpp` / `.h` / `.json` / `.yaml` / `.yml` / `.toml`）は既に「Markdown 以外の通常ファイル」として File Preview の `text` モードに落ちるため、**振り分けの追加実装は不要**。必要なのは FR-01 / FR-05 が `text` モードに効くことだけ。

**依存**: 未確定-01。Surface 層に別種別を作る場合のみ、この分岐の追加が発生する。

**受け入れ条件**
1. 上記コード拡張子のファイルを File Explorer からダブルクリックすると、`text` モードの File Preview で開き、FR-01 のハイライトと FR-05 の行番号が適用される。
2. `.md` は従来どおり Markdown 側で開く（回帰しない）。
3. 同一パスを2回開いても新規パネルが増えず、既存パネルにフォーカスが移る（既存挙動の維持）。
4. コード拡張子の追加によって `.png` 等の画像・PDF・メディアの表示モードが変わらない。

### FR-11 ハイライト配色のテーマ連動

**内容**: シンタックスハイライトの配色を、エディタの背景色・前景色テーマに合わせて切り替える。

**土台（既存）**: エディタは `themeBackgroundColor` / `themeForegroundColor` を受け取り、`applyTheme` でスクロールビュー・クリップビュー・テキストビューへ一括適用している `[実装済み: Sources/Panels/FilePreviewTextEditor.swift:20-21, 95-112]`。

**先例**: iOS 側は明暗で `xcode` / `xcode-dark` の2テーマを切り替えている `[実装済み: Packages/iOS/CmuxAgentChatUI/Sources/CmuxAgentChatUI/Artifacts/ChatArtifactSyntaxHighlighter.swift:23]`。

**受け入れ条件**
1. 明るいテーマと暗いテーマの両方で、ハイライト後の全トークン色が背景色に対して判読できる。
2. テーマを切り替えると、開いているエディタのハイライト配色が再起動なしで切り替わる。
3. ハイライトが適用されない箇所（FR-02 のフォールバック、FR-03 の閾値超過）では、従来どおり `themeForegroundColor` が使われる。

### NFR-04 ハイライトはメインスレッド外・可視範囲優先
