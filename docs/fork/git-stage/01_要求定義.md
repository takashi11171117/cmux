## 2. 現状（実コードで確認した事実）

### 2.1 Git タブは変更ファイルを表示するだけ

`GitChangesPanelView` は `FileExplorerStore.gitStatusByPath` を読んで、
変更ファイルをフォルダ畳めるツリーで表示する `[実コード: Sources/GitChangesPanelView.swift]`。
行クリックで `openFileDiffInCodeReviewColumn` を呼び、コミット未満の差分をカラムに開く
`[実コード: 同 55-60]`。**ステージ操作は無い**。

### 2.2 `GitFileStatus` は staged / unstaged を区別しない

```swift
enum GitFileStatus: Equatable {
    case modified, added, deleted, renamed, untracked
}
```
`[実コード: Sources/GitFileStatus.swift:1-3]`

### 2.3 パーサは XY を1つに潰す

`git status --porcelain=v1 -z` は `XY path` を返す (X=index, Y=work tree)。
現行の `GitStatusProvider.parseStatusChars(index:workTree:)` は「どちらかに文字が
あれば一つの status」を返す `[実コード: Sources/GitStatusProvider.swift:113-122]`。
staged / unstaged の区別は捨てている。

### 2.4 差分の CLI 経路は開いている

`openFileDiffInCodeReviewColumn` はパッチ文字列を `cmux diff -` に流す
`[実コード: Sources/AppDelegate.swift の openFileDiffInCodeReviewColumn]`。パッチの
作り方は `GitFilePatchCommand` にまとまっている `[実コード: Sources/GitFilePatchCommand.swift]`。

## 3. 業務要求（SREQ-xx）

### SREQ-01 コマンドを打たずにステージしたい

行に `+` を押せば `git add <path>` 相当が走ること。

### SREQ-02 アンステージも同じ場所でできる

行に `−` を押せば `git reset -- <path>` 相当が走ること。

### SREQ-03 変更を捨てられる

行に `↺` (discard) を押せば未ステージの変更が捨てられ、未追跡ファイルは削除できること。
**確認ダイアログを出す**。

### SREQ-04 staged と unstaged が別に見える

同じファイルで「ステージ済み修正」と「その後の未ステージ修正」の両方を持てるので、
1つのセクションに混ぜず、**「Staged Changes」「Changes」の 2 セクション**で表示する。

### SREQ-05 差分がステージ側／作業ツリー側で正しく出る

- Staged Changes の行クリック → `git diff --cached -- <path>` を表示
- Changes の行クリック → `git diff -- <path>`（現行の HEAD 比較ではなくワークツリー
  比較）を表示
- ステージも未ステージも空の場合は「差分なし」

## 4. スコープ

### 4.1 やること

- 変更ファイル一覧を 2 セクションで表示
- 行の `+` `−` `↺` ボタン
- discard は確認ダイアログを出してから実行
- 差分表示を staged / unstaged で振り分け

### 4.2 やらないこと

- **Commit ボタン**（範囲 C、今回は不要）
- **コミットメッセージ入力欄**（同上）
- Stage All / Unstage All のセクションヘッダー一括ボタン `[設計判断]` — まず個別だけ、
  必要になったら追加
- ステージ済み変更を「特定の hunk だけステージ」する UI（`git add -p` 相当）— 大工事
- Merge conflict の解決 UI

### 4.3 段階

- **STAGE 01**: データ層（`GitEntryStatus` 型、パーサ更新、既存互換維持、テスト）
- **STAGE 02**: 2 セクション表示（ボタン無し、差分振り分け）
- **STAGE 03**: 行の `+` `−` ボタン、`GitStageOperation` actor
- **STAGE 04**: 行の `↺` ボタン、確認ダイアログ

各段階で一度実機で動くことを見せる。

## 5. 先に決める必要があること

### 5.1 [決定] データ表現は staged/unstaged 2フィールドの struct

```swift
struct GitEntryStatus: Equatable, Sendable {
    let staged: GitFileStatus?
    let unstaged: GitFileStatus?
}
```

`nil` は「その側に変更なし」。`??` は staged=`M`/unstaged=`M`、`A `=staged のみ added、
`??` は untracked (unstaged 側 untracked)。既存の `GitFileStatus` は enum のまま残し、
`GitEntryStatus.displayStatus` などで従来の1状態表現も派生できるようにする（cell 側の
色分け互換）。

### 5.2 [決定] discard は確認ダイアログを出す

既存の "Move to Trash" が確認ダイアログ経由なのと同じ方針
`[実コード: Sources/FileExplorerContextMenuActions.swift の contextMenuMoveToTrash]`。
Discard は Trash に戻せない破壊的操作なので必ず確認する。

### 5.3 [要確認] ボタンの見た目と位置

案 1: 常時表示（見やすい、密度が高い）
案 2: 行 hover で表示（既存の File Explorer が hover 表示なのと合わせる）

`[要確認: 実装後にどちらが良いか判断]` 段階 03 の実装中に軽い方から試す。

## 6. 完成条件

段階 A+B（今回）は以下がすべて満たされたとき完成:

- Git タブに「Staged Changes」「Changes」の 2 セクションがある
- 同じファイルが両方に出るケース（MM）を含む git status を正しく表示する
- 行の `+` で `git add`、`−` で `git reset` が走り、一覧が数秒以内に反映される
- 行の `↺` で確認ダイアログが出て、OK で未ステージ変更が消える／未追跡が削除される
- 行クリックで staged/unstaged 側の差分が正しく開く
- 数千件変更のリポジトリでも開いた瞬間に固まらない
- git 管理外や初コミット前のフォルダでも壊れない
