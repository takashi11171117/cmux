## 1. ビルドとテストの作法

### 1.1 ビルド

```bash
./scripts/reload.sh --tag agent-first-ide            # Debug ビルド、起動しない
./scripts/reload.sh --tag agent-first-ide --launch   # 起動もする
```

- **実測 684秒**（クリーンに近い状態から）`[実測]`
- 成果物: `~/Library/Developer/Xcode/DerivedData/cmux-agent-first-ide/Build/Products/Debug/cmux DEV agent-first-ide.app`
- ログ: `/tmp/cmux-reload-agent-first-ide.log`
- 素の `xcodebuild` / untagged ビルドは禁止（他エージェントとソケット・バンドル ID が衝突する）`[規約: AGENTS.md:9-16]`

### 1.2 テスト実行 — 4つの落とし穴

#### 落とし穴1: `test-unit.sh` は `-derivedDataPath` を指定しない

```bash
# scripts/test-unit.sh の実体
exec xcodebuild -project cmux.xcodeproj -scheme cmux-unit \
  -configuration Debug -destination platform=macOS "$@"
```

`-derivedDataPath` が無いため、**そのまま実行するとタグ付きビルドの成果物を再利用せず、デフォルトの DerivedData にフルビルドし直す** `[実コード: scripts/test-unit.sh]`。`"$@"` はそのまま xcodebuild に渡るので、引数で補える。

```bash
scripts/test-unit.sh test -derivedDataPath ~/Library/Developer/Xcode/DerivedData/cmux-agent-first-ide
```

> `if [ "$#" -eq 0 ]; then set -- test; fi` という既定値処理があるため、**引数を渡すときは `test` を明示する**こと。忘れるとアクション無しで呼ばれる。

#### 落とし穴2: Swift Testing と XCTest が混在し、出力が2系統に分かれる

`cmuxTests/` は **546ファイルが `import Testing` / 120ファイルが `import XCTest`** の混在。両者は**別々の形式でログに出る** `[実測]`。

| フレームワーク | 出力例 |
|---|---|
| XCTest | `Test Suite 'MarkdownPanelTests' passed` / `Executed 28 tests, with 0 failures` |
| Swift Testing | `◇ Test run started.` / `✔ Test run with 27 tests in 4 suites passed after 1.833 seconds.` |

**`Test Suite` だけを grep すると Swift Testing 側が丸ごと見えない。** AFIDE-02 で実際にこれを踏み、55件通っているのに「28件しか走っていない」と誤読した `[実測]`。

`AGENTS.md:97` が警告する「pbxproj 未配線のテストが無言でスキップされ Executed 0 tests で緑になる」問題と**症状が酷似している**ため、件数が合わないときは配線を疑う前に**まず両方の出力形式を確認する**こと。

判定に使う grep:

```bash
grep -E "Test Suite '.*' (passed|failed) at|Executed [0-9]+ test" LOG   # XCTest 側
grep -E "◇|✔|✘|Test run with" LOG                                      # Swift Testing 側
grep -E "TEST SUCCEEDED|TEST FAILED" LOG                                # 総合判定
```

#### 落とし穴3: `test-unit.sh` は **untagged** な `cmux DEV.app` をビルドして起動する

`reload.sh --tag agent-first-ide` が作るのは `cmux DEV agent-first-ide.app` だが、`test-unit.sh` は `-scheme cmux-unit` 固定でタグを受け取る口が無く、**`cmux DEV.app`（タグなし）**をビルドする `[実測: ビルドログの Ld 行]`。テスト実行中はこのアプリが実際に起動し、`[io_exec]` / `[generic_renderer]` などのログを吐く `[実測]`。

`AGENTS.md:9-16` は「untagged builds share the default debug socket and bundle ID with other agents」と警告している。つまり **`test-unit.sh` を回している間、ユーザーのメインアプリや他エージェントの untagged ビルドと衝突しうる**。`-derivedDataPath` を渡してもプロダクト名は変わらないので、これは回避できない。

実務上の意味: **テストを回すときはユーザーの cmux が起動中でないか気にする**。CI では単独環境なので問題にならない。

#### 落とし穴4: フルスイートはローカルで完走しない

`scripts/test-unit.sh` を絞り込みなしで実行すると、**5スイート目の `AppDelegateShortcutRoutingTests` が `started` のまま3分以上進まずハングする** `[実測]`。

- 他スイートはいずれも数秒で完了しているので、明確に異常
- ハング中もログは伸び続け、**49万行**に膨張する。中身は終了しなかった `cmux DEV` プロセスの `[generic_renderer]` / `[io_exec]` ログ
- `pkill -f "xcodebuild.*cmux-unit"` するまで終わらない

ハングまでに観測した失敗 `[実測]`:

| スイート | 結果 |
|---|---|
| `AccessibilityInsertTextRegressionTests` | 3件中 **2 failures** |
| `AppDelegateIssue2907RoutingTests` | 28件中 **3 failures** |

**失敗もハングも AppDelegate / Accessibility 系（GUI 依存）に集中している。** `AGENTS.md` は「tagged macOS GUI checks は Mac mini フリートで走らせる」と定めており、この領域をローカルで回すのは想定された使い方ではない。

> **これらが upstream 由来で元から赤いのか、このマシン固有（アクセシビリティ権限・フォーカス・ウィンドウサーバ）なのかは切り分けていない** `[要調査]`。**「既存テストは全部通る」と書いてはならない。**

**回帰判定の実務**: 触った領域のテストを `-only-testing` で絞って回す。フルスイートの緑判定は `scripts/verify-remote.sh mac --tag agent-first-ide` かCI に委ねる。

```bash
scripts/test-unit.sh test -derivedDataPath ~/Library/Developer/Xcode/DerivedData/cmux-agent-first-ide \
  -only-testing:cmuxTests/FilePreviewTextEditorTextKitTests \
  -only-testing:cmuxTests/FilePreviewReloadTests \
  -only-testing:cmuxTests/FilePreviewReloadCompletionTests \
  -only-testing:cmuxTests/FilePreviewKindResolverTests \
  -only-testing:cmuxTests/MarkdownPanelTests
```

この5ファイル = 55テスト（Swift Testing 27 + XCTest 28）が本 fork の回帰ラインで、**全通過を確認済み** `[実測: 2026-08-17]`。

### 1.3 新規ファイルの pbxproj 配線（自動化ツールは無い）

**`.swift` を置くだけでは Xcode に認識されない。** テストなら無言でスキップされ CI が緑になる `[規約: AGENTS.md:97]`。

**リポジトリに pbxproj へファイルを追加するツールは存在しない**（`scripts/` にあるのは `normalize-pbxproj.py` / `check-pbxproj.sh` / `lint-pbxproj-test-wiring.sh` の3本で、いずれも検査と整形のみ）`[実測]`。手で4エントリを足すことになる。

| # | セクション | 形 |
|---|---|---|
| 1 | `PBXBuildFile` | `<buildUUID> /* Foo.swift in Sources */ = {isa = PBXBuildFile; fileRef = <refUUID> /* Foo.swift */; };` |
| 2 | `PBXFileReference` | `<refUUID> /* Foo.swift */ = {isa = PBXFileReference; lastKnownFileType = sourcecode.swift; path = Panels/Foo.swift; sourceTree = "<group>"; };` |
| 3 | `PBXGroup` の `children` | `<refUUID> /* Foo.swift */,` |
| 4 | `PBXSourcesBuildPhase` の `files` | `<buildUUID> /* Foo.swift in Sources */,` |

**注意点**:

- **`path` は app target とテストで書き方が違う。** `Sources/Panels/` 配下は `path = Panels/Foo.swift`（`Sources/` は付けない）、`cmuxTests/` 配下は `path = FooTests.swift`（ディレクトリなし）`[実コード: 既存エントリ]`
- UUID は **24文字の16進大文字**。既存は意味のあるプレフィックスを使っている（`F11E5227…`, `C0DE4995…`）ので、新規機能ごとにプレフィックスを決めると追跡しやすい
- **`PBXSourcesBuildPhase` はプロジェクトに5つある**（`grep -n "isa = PBXSourcesBuildPhase"`）。`cmux` と `cmuxTests` を取り違えないこと
- `PBXGroup.children` は `normalize-pbxproj.py` が**ソートしない**（ナビゲータの表示順を保つため）。`PBXBuildFile` / `PBXFileReference` はソートされるので挿入位置は任意

> **⚠️ `Sources/` 直下のファイルと `Sources/Panels/` 配下でパスの書き方が違う。** 配線スクリプトを使い回すと、直下に置いたファイルに `path = "Panels/Foo.swift"` を書いてしまう。この間違いは `check-pbxproj.sh` を通り、**ビルド時に `Build input file cannot be found` で落ちる**。あわせてグループ（ナビゲータの表示位置）も対応するディレクトリのものを選ぶこと。`path` だけ直してもビルドは通るが、Xcode 上では別フォルダの中に見える。

> **⚠️ `+` を含むファイル名は `path` を引用符で囲むこと。** pbxproj は OpenStep plist で、`[A-Za-z0-9_./]` 以外を含む文字列はクォートが要る。`Type+Feature.swift` 命名（`FilePreviewPanel+Reload.swift` など、リポジトリ全体で使われている慣習）はまさにこれに該当する `[実コード: cmux.xcodeproj/project.pbxproj:3941]`。
>
> ```
> path = "Panels/FilePreviewPanel+SaveConflict.swift";   ← 正しい
> path = Panels/FilePreviewPanel+SaveConflict.swift;     ← プロジェクトが壊れる
> ```
>
> **`./scripts/check-pbxproj.sh` はこの破損を検出しない。** クォートを落としたまま check も `lint-pbxproj-test-wiring.sh` も通り、`xcodebuild` を実行して初めて次が出る `[実測: AFIDE-12 で実際に踏んだ]`:
>
> ```
> xcodebuild: error: Unable to read project 'cmux.xcodeproj'.
>   Reason: The project 'cmux' is damaged and cannot be opened due to a parse error.
> ```
>
> `plutil -lint` も使えない（pbxproj は JSON/XML plist ではないため常に失敗する）。**確実な検証は `xcodebuild -project cmux.xcodeproj -list` が成功すること。** 配線後はこれを回す。

**実用的なやり方**: 同種の既存ファイル1本をアンカーにし、その4エントリそれぞれの直後に挿入する。インデントも取り違えない（グループは4タブ、SourcesBuildPhase は5タブ）。挿入後に必ず次を回す。

```bash
python3 scripts/normalize-pbxproj.py cmux.xcodeproj/project.pbxproj
./scripts/check-pbxproj.sh
./scripts/lint-pbxproj-test-wiring.sh                    # 件数が増えているか確認
xcodebuild -project cmux.xcodeproj -list > /dev/null     # ★ 構文破損はこれでしか分からない
```

`lint-pbxproj-test-wiring.sh` の出力する件数（`checked N test files`）が**増えていること**が、テストが実際にビルドへ入った証拠になる。

### 1.4 JSON 資産は再シリアライズせず、テキストとして挿入する

`web/data/cmux.schema.json` / `web/messages/{en,ja}.json` / `Resources/Localizable.xcstrings` はいずれも JSON だが、**`json.load` → `json.dumps` で書き戻すとファイル全体が書き換わる** `[実測]`。

| ファイル | 元の形式 | 再シリアライズすると |
|---|---|---|
| `web/data/cmux.schema.json` | prettier（短い配列・オブジェクトは1行） | `"enum": ["newline", "menu"]` が3行に展開され、**2キー追加のはずが 241 追加 / 50 削除**になった |
| `Resources/Localizable.xcstrings` | Xcode 生成（5,000超のキー） | キー順とインデントが変わり、**6キー追加のはずが 5,181 追加 / 7,844 削除**になった |

どちらもレビュー不能な差分になり、upstream 追従時のコンフリクト面も跳ね上がる。**必ず既存エントリをアンカーにしたテキスト置換で挿入する。** 挿入後に `python3 -c "import json; json.load(open(...))"` で妥当性を、`git diff --numstat` で差分が最小であることを確認する。

`Localizable.xcstrings` はキーがアルファベット順に並んでいるので、挿入位置もそれに従う（`fileEditorLineNumbers` < `fileEditorSyntaxHighlight` < `fileEditorWordWrap`）。区切り記法（`"key": {` か `"key" : {`）はファイルによって違うので、書く前に実物を `grep` で確認する。

### 1.5 テストファイルを書くときの作法

**`@testable import cmux` と単純に書くとタグ付きビルドで落ちる。** タグ付き Debug ビルドはプロダクト名が `cmux DEV <tag>` になるためモジュール名が `cmux_DEV` になる。既存テストは全て条件付き import で受けている `[実コード: cmuxTests/FilePreviewKindResolverTests.swift:4-8]`。

```swift
import Foundation
import Testing

#if canImport(cmux_DEV)
@testable import cmux_DEV
#elseif canImport(cmux)
@testable import cmux
#endif
```

その他:

- 新規テストは **Swift Testing**（`import Testing` / `@Suite` / `@Test`）。`import XCTest` を新規に書かない `[規約: skills/cmux-testing/SKILL.md]`
- `@Test(arguments:)` にラベル付きタプルの配列を渡すのは避け、テスト内でループする方が確実（マクロの受理条件が読みにくく、失敗するとコンパイルエラーの原因が分かりにくい）`[設計判断]`
- テストは**実行時挙動**を検証する。ソース・pbxproj・plist の grep テストは書かない `[規約: skills/cmux-testing/SKILL.md]`

### 1.5 AppKit をテストするときに踏んだもの

| 症状 | 原因と対処 |
|---|---|
| `textView.undoManager` が `nil` | `NSResponder.undoManager` はレスポンダチェーンを遡って**ウィンドウ**から取る。テストで組み立てただけのビューにはウィンドウが無い。`NSTextViewDelegate.undoManager(for:)` を実装したスタブを `delegate` に挿すのが AppKit 公式の差し込み口 `[実測]` |
| `private(set)` なプロパティに別ファイルの `extension` から代入できない | Swift の `private(set)` は**宣言と同じファイル**でのみ setter が見える。型の `extension` を別ファイルに切ると書けなくなる。setter を `internal` にして DocC で書き込み元を明示するか、`extension` を同じファイルに置く `[実測]` |
| `NSRulerView` の幅が更新されない | 再計算のキャッシュキーを「行数」だけにしていたため、**フォント変更（ズーム）で再測定されなかった**。行数とフォントの両方をキーにする `[実測: AFIDE-10 で実際に踏んだ]` |

## パネルの開閉ボタンは「パネル自身」にも置く

コードレビューカラムの開閉を、ターミナル側タブバーの組み込みボタン
(`CmuxSurfaceTabBarBuiltInAction.toggleCodeReview`) だけで提供したところ、
「on/off が入っていない」と繰り返し指摘された。

原因は発見性。タブバーのボタンは *開く* 側の入口としては機能するが、
カラムが開いている状態でそれを *閉じる* には、視線をカラムから離して
別領域のアイコン列から該当アイコンを探す必要がある。閉じる操作の起点は
閉じたい対象の上にあるのが自然。

対策として `CodeReviewPanelView` のヘッダー右端に非表示ボタンを置いた
(`Sources/CodeReviewPanelView.swift` の `header`)。開くのはタブバー、
閉じるのはカラム自身、という双方向の導線になる。

一般化: 表示/非表示を持つ領域を追加したら、**その領域自身の上に閉じる操作**を
必ず用意する。メニューとショートカットと外部タブバーだけでは足りない。

## ユーザー設定が既定値を隠していないかを先に確かめる

`CmuxSurfaceTabBarButton.defaults` にボタンを足しても、`~/.config/cmux/cmux.json`
に `surfaceTabBarButtons` が書かれていれば既定値は使われない。
「ボタンが出ない」と言われたとき、実装ではなく設定が原因のことがある。

確認は次の順で行う（今回は設定に該当キーが無く、既定値が効いていた）。

```bash
grep -n -i "tabbar\|button" ~/.config/cmux/cmux.json
```

なお `cmux.json` は行コメントを含む JSONC なので、`json.load` は
`JSONDecodeError` で落ちる。素朴にパースして「設定が壊れている」と
誤診しないこと。

## PRODUCT_NAME をコマンドラインで渡すとビルドが壊れる

fork を別名アプリ (`cmux AFIDE`) として出すため `xcodebuild ... PRODUCT_NAME="cmux AFIDE"`
としたところ、19 個のエラーで失敗した。

```
error: Multiple commands produce '.../cmux AFIDE.bundle/Contents/Info.plist'
error: Multiple commands produce '.../cmux_AFIDE.swiftmodule/arm64-apple-macos.swiftmodule'
```

コマンドラインのビルド設定は**全ターゲットに適用される**。このプロジェクトは
`Bonsplit_Bonsplit.bundle` や `PostHog_PostHog.bundle` など SPM のリソースバンドルを
多数含み、それらまで `cmux AFIDE.bundle` に改名されて出力先が衝突する。

`scripts/reload.sh` は同じことを別の方法で達成している。`PRODUCT_NAME` は渡さず、
ビルド後に `.app` をコピーして `Info.plist` の `CFBundleName` /
`CFBundleDisplayName` / `CFBundleIdentifier` を PlistBuddy で書き換える。
`scripts/fork/release-afide.sh` もこの方式にした。

`PRODUCT_BUNDLE_IDENTIFIER` は渡しても問題ない（バンドル名を変えないため）。ただし
サイドバー拡張のために `CMUX_SIDEBAR_EXTENSION_POINT_ID` を合わせて渡す必要がある。
`INFOPLIST_KEY_CFBundleName` はアプリターゲット専用のキーなので安全。

## Sparkle の鍵生成は secrets のパーミッションを 644 に戻す

`scripts/sparkle_generate_keys.sh` は `SPARKLE_ENV_FILE` を awk で書き直すため、
事前に `chmod 600` してあっても実行後は 644 になる。秘密鍵が入るファイルなので、
生成後に必ず権限を確認すること。

`scripts/fork/release-afide.sh` は起動時に `stat -f "%Lp"` で確認し 600 でなければ
締め直す。「一度設定したから大丈夫」と考えないこと。

## @MainActor 型の static 純粋関数は nonisolated にする

`CodeReviewPanelState.clampedWidth` は状態を触らない純粋関数だが、型が `@MainActor`
のため static メソッドも隔離され、テストからこう弾かれた。

```
error: call to main actor-isolated static method 'clampedWidth(_:availableWidth:)'
in a synchronous nonisolated context
```

テスト側に `@MainActor` を付ければ通るが、それは症状を隠すだけ。隔離が不要なものに
隔離が付いていること自体が誤りなので、実装を `nonisolated static func` にした。
呼び出し元が MainActor でも問題なく呼べる。

**テストが書きにくいときは、まず実装の隔離が過剰でないかを疑うこと。**

## 画面ロック中は GUI 検証が一切できない

エージェント側から手動テストを実行しようとして、次の症状に順に遭遇した。

- `System Events` の `count windows` が 0（`cmux DEV` プロセス自体は見えている）
- `set frontmost to true` を送っても変わらない
- `screencapture` が壁紙のみを返す（メニューバーも Dock も写らない）

原因は画面ロック。`caffeinate -u` はディスプレイを起こせてもロックは解除しない。
`cmux` 内部の `list-windows` は 1 を返すため、**アプリ側の状態だけ見ていると
「ウィンドウはあるのに AX から見えない」という誤った結論に進む**。

判定方法として、`screencapture` にメニューバーが写っているかを先に見るとよい。
写っていなければ GUI 検証は不可能であり、原因究明に時間を使わずユーザーに解除を
依頼する。

## fork の bundle ID は放っておくと本家のソケットを奪う

`cmux AFIDE` の bundle ID を `com.cmuxterm.app.afide` にしただけでは、ソケットは
本家と分離されない。`SocketPathMarkerFiles.variant` の判定はこうなっている。

```
com.cmuxterm.app.nightly[.*]  -> .nightly
com.cmuxterm.app.staging[.*]  -> .staging
com.cmuxterm.app.debug[.*]    -> .dev（タグごとに分離）
それ以外                       -> .stable   ← fork はここへ落ちる
```

`.stable` は本家そのものなので、ソケットもマーカーも共有してしまう。

- 両方起動すると後から起動した方がソケットを奪う
- マーカー (`~/.local/state/cmux/last-socket-path`) を互いに上書きする
- `cmux send` がどちらのアプリに届くか不定になる

**エージェントに別ペインを操作させる用途では、これは黙って誤爆する。**
コマンドは成功し、ただ宛先が違うだけなので、どちらの側からも検知できない。

`SocketPathVariant.fork(slug:)` を追加し、`forkBundleIdentifierPrefixes` に
載せた識別子をそこへ振り分けるようにした。判定は `.stable` フォールバックの
直前に置く（先に置くと debug の枝を奪う恐れがある）。

回帰テストは
`Packages/macOS/CmuxSettings/Tests/.../SocketPathForkVariantTests.swift`。
fork が分離されることに加え、**既存の4系統が元の variant のままであること**も
固定してある。新しい判定を足すときに他を巻き込んでいないかを見るため。

なお `SocketPathVariant` を switch している箇所は3つある
(`markerFileName` / `tmpPath` / `MobileHostIdentity`)。case を足したら
コンパイラが網羅漏れを教えてくれるが、`tmpPath` はマーカーのパスであって
ソケット本体ではない点に注意。ソケットは
`SocketPathMarkerFiles.defaultSocketPath` が返す。

### テストのフィルタは型名で指定する

`swift test --filter "SocketPathVariant fork isolation"` のように Suite の
表示名を渡すと **0 件実行で緑になる**。`--filter SocketPathForkVariantTests`
と型名で指定すること。「Executed 0 tests」は緑ではない。


## Nucleo FFI の dylib が無いと署名で落ちる（cargo が PATH に無いだけ）

リリースが署名の直後にこう落ちた。

```
error: missing bundled Nucleo FFI library at
  .../cmux AFIDE.app/Contents/Frameworks/libcmux_command_palette_nucleo_ffi.dylib
```

原因は `cargo` が PATH に無かったこと。rustup は `~/.cargo/bin` に入れるが、
非ログインシェルにはそこが載っていない。

厄介なのは、ビルドと検証で扱いが食い違う点。

- `scripts/build-command-palette-nucleo-ffi.sh` は cargo が無いと
  **warning を出して exit 0**（オプショナル扱い）
- `scripts/sign-cmux-bundle.sh` は
  `verify-command-palette-nucleo-ffi-artifact.sh` を呼び、dylib が無いと **error**

結果、ビルドは黙って成功し、20分後の署名で初めて落ちる。Debug ビルドは検証を
通らないので、日常のタグ付きリロードでは永久に気付けない。

`scripts/fork/release-afide.sh` の pre-flight で次を見るようにした。

- `~/.cargo/bin` を PATH に足す
- `cargo` の存在を必須ツールとして検査
- `aarch64-apple-darwin` と `x86_64-apple-darwin` の両方を
  `rustc --print target-libdir --target <t>` で検査

universal ビルドなので**片方欠けてもそのアーキテクチャだけ FFI が作られず**、
やはり署名時に同じエラーになる。ここも先に弾く。

**教訓**: 長い工程の途中で落ちる前提条件は、全部 pre-flight に集める。
「ビルドがオプショナル扱いするもの」を「後工程が必須扱いする」構図は、
所要時間ぶんだけ損をする。

## keychain-access-groups は provisioning profile 無しでは起動できなくする

署名も公証も Gatekeeper も通っているのにアプリが起動しない、という状態になった。

```
spctl -a -vvv → accepted / source=Notarized Developer ID     ← 問題なし
open          → The application cannot be opened for an unexpected reason
                Error Domain=RBSRequestErrorDomain Code=5 "Launch failed."
                NSPOSIXErrorDomain Code=163 "Launchd job spawn failed"
```

原因は entitlements の `keychain-access-groups`。これは provisioning profile に
よる裏付けが要る特権 entitlement で、`Contents/embedded.provisionprofile` が
無いと launchd が起動そのものを拒否する。

本家は CI シークレット (`APPLE_RELEASE_PROVISIONING_PROFILE_BASE64`) から
profile を埋め込んでいる (`.github/workflows/release.yml`)。fork 用の
リリース手順にはその工程が無かったため、entitlement だけが残っていた。

fork はキーチェーングループを共有しないので、entitlement 側を落とした。
`scripts/fork/afide.entitlements.tmpl` から削除し、release スクリプトに
「profile 無しでこの entitlement を持たせない」ガードを入れてある。

**罠なのは、署名・公証・Gatekeeper がすべて成功する点。** 検証系のコマンドは
全部 OK を返すので、実際に `open` するまで気付けない。リリース手順に
「成果物を一度起動する」を含めること。

なお同種の entitlement を将来足すなら、profile の埋め込みが先に要る。

## fork のバージョンはタグから焼き込まないと自動更新が永久に来ない

v0.1.1 を配ったあと、アプリの `CFBundleShortVersionString` が **0.64.22**
（本家 cmux の値）のままだった。タグは v0.1.1、Cask は 0.1.1、しかしアプリ本体と
appcast は 0.64.22 を名乗る。

この状態だと Sparkle は永久に更新を出さない。appcast が広告するバージョンを、
インストール済みのアプリが既に報告しているため、比較して「新しくない」と結論する。
エラーも警告も出ず、ただ静かに何も起きない。

`scripts/fork/release-afide.sh` はタグから `VERSION` を導出し、リネーム時に
`CFBundleShortVersionString` と `CFBundleVersion` を焼き込む。焼けたかを
PlistBuddy で読み直して検証し、appcast 生成後には
`sparkle:shortVersionString="$VERSION"` が含まれるかも確認する。

タグは `v1.2.3` 形式のみ受け付ける（`v0.1.2-beta` は拒否）。Sparkle の比較は
dotted numeric を前提とするため。

## notarytool --wait は接続断で最初からやり直しになる

`xcrun notarytool submit --wait` は 1 本の長時間接続を保持する。Apple 側に
切られると

```
Submission ID received
  id: bb3be954-...
Error: HTTPClientError.connectTimeout
```

と、**提出は成功しているのにコマンドは非ゼロ終了する**。スクリプトを再実行すると
また新規提出になり、待ち時間が積み上がる。

提出とポーリングを分けた。id は待機の前に出力されるので、接続が切れても
`xcrun notarytool info <id>` で追える。60分待っても終わらなければ、その id を
出力して終了する（手で待ち直せる）。

なお公証サービスが詰まったときの回復判定は、**小さなファイルを提出してみる**のが
確実。21MB の zip が 1 分半で Accepted になった時点で、滞留していた大きな提出は
諦めて出し直した方が早いと判断できた。

## リリース手順に「成果物を起動する」を入れる

`keychain-access-groups` の件で学んだこと。署名・公証・Gatekeeper がすべて成功
しても起動しないバンドルは作れてしまう。検証コマンドは全部 OK を返す。

`release-afide.sh` は appcast 生成の前に、署名済みアプリを一時ディレクトリへ
コピーして `open` し、プロセスが立つのを確認してから公開へ進む。立たなければ
公開しない。
