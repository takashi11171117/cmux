## 1. Why

cmux の File Preview / Markdown パネルは既に編集可能なテキストエディタである（編集・Undo・Find・保存・外部変更検知が実装済み）`[実コード: Sources/Panels/FilePreviewTextEditor.swift:171-176, Sources/Panels/FilePreviewPanel.swift:1301-1339]`。エージェントの出力を読むために外部エディタへ出る必要がなくなる最後の2要素が **シンタックスハイライト** と **行番号** である。

この2つは「新しいエディタを作る」話ではない。既存の `SavingTextView`（明示的に構築された TextKit 1 スタック）に、属性付与とルーラ描画を **足す** 話である。本書の価値は「既存コードのどこをどう触るか」を確定させることにあり、新規アーキテクチャの提案ではない。

## 2. 設計方針

### 2.1 5つの原則

| # | 原則 | 根拠 |
|---|---|---|
| P-1 | **新しい `PanelType` を作らない。既存 `.filePreview` / `.markdown` を拡張する** | §5 D-1 |
| P-2 | **`SavingTextView` の TextKit 1 構築を1行も崩さない**（`textLayoutManager == nil` を保つ） | NFR-07 / `[実コード: cmuxTests/FilePreviewTextEditorTextKitTests.swift:42]` |
| P-3 | **ハイライトエンジンを具体ライブラリに直結させず、値型の seam を1枚挟む**（未確定-02 を実装開始のブロッカーにしない） | NFR-11 / §5 D-2 |
| P-4 | **複数入口を持つ振る舞いは共有アクション1本に集約する**（分岐を各入口へ足さない） | `[規約: AGENTS.md:103-105, skills/cmux-shared-behavior/SKILL.md「Shared entrypoints」]` |
| P-5 | **差分を `Sources/Panels/` と `Packages/macOS/CmuxSettings*` と `docs/fork/` に閉じる** | NFR-08 |

### 2.2 P-5 に伴う意図的な逸脱（1件）

`skills/cmux-architecture/SKILL.md:10-16` は新しいドメインを Swift Package として切り出すことを求める。しかし新規パッケージの追加は `cmux` と `cmux-unit` の **両ターゲット** に pbxproj エントリを要し `[規約: skills/cmux-architecture/SKILL.md:18]`、さらに `cmux.xcworkspace/contents.xcworkspacedata` のグループ更新（`python3 scripts/check-workspace-package-groups.py --write`）を伴う `[規約: skills/cmux-architecture/SKILL.md:20]`。これは fork の差分を upstream の中枢ファイルへ広げる。

本書では **新規パッケージを作らず**、新規型は `Sources/Panels/` 配下の app-target ファイルとして追加する。同スキル自身が「境界が存在するのは複数の consumer が必要とするとき」としており `[規約: skills/cmux-architecture/SKILL.md:14]`、本設計の新規型の consumer は `FilePreviewTextEditor` 系のみで、この条件を満たさない。ただし app-target 新規ファイルにも **1ファイル1型 / 自由関数禁止 / DocC** は適用する `[規約: skills/cmux-architecture/SKILL.md:54-59, 80, 63]`。

## 5. 主要な設計判断

### D-1 【最上位・未確定-01 への回答】Panel 層に足す。新しい `PanelType` は追加しない

**結論**: `FilePreviewPanel` / `MarkdownPanel`（Panel 層）の拡張として実装する。`PanelType` にも `CmuxSurfaceType` にもケースを追加しない。

**根拠1: `CmuxSurfaceType` は Session Restore と無関係**

`CmuxSurfaceType` の参照はリポジトリ全体で `Sources/CmuxConfig.swift` の2行のみ `[実コード: Sources/CmuxConfig.swift:1611, 1620]`（`grep -rn "CmuxSurfaceType" --include="*.swift" .` の全件）。設定ファイルの宣言的レイアウトスキーマであり、復元経路には現れない。01 §6 訂正の前提は実コードと一致しない（要件定義 §0 で既に指摘済み）。

**根拠2: 新 `PanelType` ケースは fork にとって片道切符になる**

`PanelType.init(from:)` は未知の raw value に対して `DecodingError.dataCorruptedError` を **throw する** `[実コード: Sources/Panels/Panel.swift:66-69]`。そして `SessionWorkspaceSnapshot.panels` は `[SessionPanelSnapshot]`（Optional ではない）で合成 `Codable` を使う `[実コード: Sources/SessionPersistence.swift:1839]`。したがって1つのパネルの type が読めないだけで **workspace snapshot 全体のデコードが失敗する**。

fork が独自ケース（例 `codeEditor`）を足すと、その fork でセッションを保存したユーザーが upstream ビルドや以前のビルドに戻った瞬間、セッションファイルが復元不能になる。これは NFR-01（Session Restore を壊さない、最優先）に真正面から反する。fork という文脈では特に、ビルドの行き来が起きうる。

**根拠3: 追加の必要がない**

`PanelType` には既に `.filePreview` と `.markdown` がある `[実コード: Sources/Panels/Panel.swift:10, 9]`。`FilePreviewKindResolver.textExtensions` は `swift` / `ts` / `tsx` / `js` / `json` / `yaml` / `yml` / `toml` / `py` / `rs` / `go` / `cpp` / `h` などコード拡張子を既に含み `[実コード: Sources/Panels/FilePreviewPanel.swift:669-675]`、`.text` モードへ落ちる。FR-01 / FR-05 は `.text` モードのエディタに効かせるだけでよい。

**この判断が FR に与える形**

- FR-01 / FR-05: `FilePreviewTextEditor` + `SavingTextView` の変更で閉じる。`Sources/Workspace.swift` は**触らない**（NFR-08 受け入れ条件3を満たす）
- FR-07: `FilePreviewPanel` と `MarkdownPanel` の両方が `FilePreviewTextEditingPanel` を実装している `[実コード: Sources/Panels/FilePreviewPanel.swift:975, Sources/Panels/MarkdownPanel.swift:16]` ため、衝突コーディネータはプロトコル越しに両方へ効く
- FR-10: 追加分岐なし（§10.1）

### D-2 Highlightr の流用可否

**結論: `Packages/iOS/CmuxAgentChatUI` 経由の「流用」は不可。Highlightr 単体の「採用」は技術的には可能だが本書では決めない（未確定-02 のまま）。**

#### 流用が不可な理由（3点、いずれも実コード確認済み）

1. **macOS アプリ本体は `CmuxAgentChatUI` を一切リンクしていない**。`cmux.xcodeproj/project.pbxproj` に `CmuxAgentChatUI` の出現は0件。`cmux.xcworkspace/contents.xcworkspacedata:48` の `Packages (iOS)` グループにファイルツリーとして現れるだけで、これはリンクではない。

### D-4 保存衝突 UI は「シートではなくパネル内バナー」

**結論**: `NSAlert` のモーダルシートではなく、パネルヘッダ直下に条件付きで現れる SwiftUI バナーにする。

**理由**

- NFR-14 は「常時表示 UI を増やさない」であって、条件付き UI を禁じてはいない。バナーは `isDirty && 衝突あり` のときだけ現れる
- モーダルシートはウィンドウ全体を止める。cmux は複数のエージェントセッションが同時に走る前提のアプリであり、1ファイルの衝突で他ペインの操作を止めるのは思想に反する `[メモ由来: REQ-01 / 要件定義 §0]`
- 「選択を出している間にさらに外部変更が起きてもバッファが失われない」（FR-07 AC5）は、モーダルより非モーダルのほうが素直に書ける

**ただしテスト容易性は `NSAlert` 経路の先例に倣う**。`BrowserHTTPBasicAuthPrompt` は `alertFactory` と `presentAlert: BrowserAlertPresenter` を引数で注入し、テストが実際のダイアログを出さずに検証できるようにしている `[実コード: Sources/Panels/BrowserHTTPBasicAuthPrompt.swift:52-58, Sources/Panels/BrowserPanel.swift:1059-1078]`。本設計でも解決の適用を `FilePreviewSaveConflictCoordinator` に閉じ、View 抜きで単体テストできる形にする。

衝突の重複統合は `BrowserHTTPBasicAuthPromptCoordinator` の形を参考にする。同クラスは同一 protection space の要求を1件にまとめ、キュー長に上限を持つ `[実コード: Sources/Panels/BrowserHTTPBasicAuthPromptCoordinator.swift:14-15, 38-48]`。本設計は「1パネル = 1ファイル」なので**キューではなく最新の1件で上書き**する（§9.2）。

### D-5 設定アクセサは既存 `FilePreviewWordWrapSettings` に形を揃える

`skills/cmux-architecture/SKILL.md:77` は namespace-enum（`enum Foo { static func bar() }`）の新設を禁じている。しかし `fileEditor.*` の既存アクセサ `FilePreviewWordWrapSettings` はまさにその形であり `[実コード: Sources/Panels/FilePreviewWordWrapSettings.swift:9-21]`、`@AppStorage(FilePreviewWordWrapSettings.key)` として2つの View から使われている `[実コード: Sources/Panels/FilePreviewPanel.swift:1381, Sources/Panels/MarkdownPanelView.swift:32]`。

**判断**: 兄弟キー2本も同じ形（`Sources/Panels/FilePreviewSyntaxHighlightSettings.swift` / `Sources/Panels/FilePreviewLineNumberSettings.swift`）で書く。`[設計判断]`

**理由**: `@AppStorage` は `key: String` と `defaultValue` の静的な組を必要とし、インスタンスを注入できない。ここだけ別の形にすると `fileEditor.*` の3キーが2種類の書き方に割れ、次に触る人が判断できなくなる。スキル自身も「既存 app-target コードを盲目的に retrofit するな」としている `[規約: skills/cmux-architecture/SKILL.md:124]`。

一方、**判定ロジックを持つ新規型（`FilePreviewHighlightPolicy` など）は namespace-enum にしない**。`struct` にして `UserDefaults` や閾値を `init` で受け取り、テストから注入できるようにする `[規約: skills/cmux-architecture/SKILL.md:84-88]`。

## 6. Model（新規型）

すべて値型または `@MainActor` クラス。AppKit 依存を持つのは `FilePreviewHighlightPalette`（`NSColor`）と `FilePreviewLineNumberRulerView`、`FilePreviewSyntaxHighlightController` のみ。

```swift
// 色を持たない意味論トークン。エンジンとテーマを分離する要。
enum FilePreviewTokenRole: Sendable { case keyword, string, comment, number, type, attribute, plain }

struct FilePreviewHighlightRun: Sendable, Equatable {
    let range: NSRange
    let role: FilePreviewTokenRole
}

protocol FilePreviewSyntaxHighlighting: Sendable {
    /// `range` に交差するトークンだけを返す。エンジンは範囲外を返してよいが、
    /// 呼び出し側は `range` でクリップする。
    func runs(for text: String, language: String, range: NSRange) async -> [FilePreviewHighlightRun]
}

enum FilePreviewHighlightDecision: Sendable, Equatable {
    case highlight(language: String)
    case skippedForSize
    case skippedNoLanguage
}

struct FilePreviewHighlightPolicy: Sendable {
    let maximumHighlightBytes: Int
    let languages: FilePreviewSyntaxLanguage
    func decision(path: String, byteCount: Int) -> FilePreviewHighlightDecision
}

/// 論理行の開始オフセット（UTF-16）。二分探索で行番号を引く。
struct FilePreviewLineIndex: Sendable, Equatable {
    private let lineStarts: [Int]
    init(text: NSString)
    var lineCount: Int { lineStarts.count }
    func lineNumber(atUTF16Offset offset: Int) -> Int      // 1 始まり
    func isLineStart(utf16Offset: Int) -> Bool
    /// 編集後の増分更新。`editedRange` 以前は不変、以降は `changeInLength` だけシフト。
    func patched(editedRange: NSRange, changeInLength: Int, text: NSString) -> FilePreviewLineIndex
}

struct FilePreviewSaveConflict: Sendable, Equatable {
    let filePath: String
    let diskContent: String
    let detectedAt: Date
}

enum FilePreviewSaveConflictResolution: Sendable, Equatable { case reload, compare, keepMine }

struct FilePreviewExternalOpenLocation: Sendable, Equatable {
    let fileURL: URL
    let line: Int?     // 1 始まり。nil は行指定なし（従来挙動）
}
```

## 7. シンタックスハイライトの設計（FR-01 / FR-02 / FR-03 / FR-11）

### 7.1 差し込み位置

現状のテキスト構築経路は次の3点である。

1. `FilePreviewTextEditor.makeNSView(context:)` — `SavingTextView.makeFilePreviewTextView()` を作り `textView.string = panel.textContent` を代入 `[実コード: Sources/Panels/FilePreviewTextEditor.swift:40-47]`
2. `FilePreviewTextEditor.updateNSView(_:context:)` — `textView.string != panel.textContent` のとき、選択範囲とスクロール位置を保存しつつ `textView.string` を差し替える `[実コード: 同 :72-92]`
3. `Coordinator.textDidChange(_:)` — ユーザー入力を `panel.updateTextContent(textView.string)` へ流す `[実コード: 同 :124-128]`

**`textView.string` への代入は `NSTextStorage` の属性を全消去する。** したがってハイライトの再適用トリガはこの3点＋テーマ変更＋フォント変更である。

差し込みは `Coordinator` に `FilePreviewSyntaxHighlightController` を1つ持たせる形にする。`Coordinator` は既に `NSTextViewDelegate` であり `panel` の参照を持つ `[実コード: 同 :114-121]`。

```
FilePreviewTextEditor.makeNSView
  └─ coordinator.highlightController.attach(textView:scrollView:policy:palette:)   // ハイライト有効時のみ生成（NFR-03）
FilePreviewTextEditor.updateNSView
  ├─ coordinator.highlightController?.setEnabled(syntaxHighlight)                  // 設定のライブ反映（FR-04 AC1）
  ├─ coordinator.highlightController?.setPalette(FilePreviewHighlightPalette(background: themeBackgroundColor, foreground: themeForegroundColor))
  └─ （string 差し替えの直後に）coordinator.highlightController?.invalidateAll()
Coordinator.textDidChange
  └─ coordinator.highlightController?.noteTextDidChange()                          // デバウンス開始
```

`SavingTextView` 自体には**フィールドを追加しない**。既存は `weak var panel` / `previewFontSize` / チョード状態 / フォント監視の4つだけ `[実コード: 同 :241-244]` であり、ここに状態を足すと `makeFilePreviewTextView()` の純粋さ（TextKit 1 構築だけを担う）が崩れる。ズームとフォント変更の通知だけは必要なので、`setPreviewFontSize(_:)` `[実コード: 同 :335-343]` と `applyCurrentPreviewFont()` `[実コード: 同 :345-349]` の後に `NSTextView` の既存 API（`NSView.needsDisplay` とルーラの `invalidateHashMarks()`）が走る形にする（§8.4）。

### 7.2 言語判定（FR-02）

`FilePreviewSyntaxLanguage` に拡張子 → 言語 ID の表を持つ。表の内容は `ChatArtifactSyntaxHighlightPolicy.languagesByExtension`（52 拡張子）`[実コード: Packages/iOS/CmuxAgentChatUI/Sources/CmuxAgentChatUI/Artifacts/ChatArtifactSyntaxHighlightPolicy.swift:8-64]` を macOS 側へ**複製**する。共有パッケージ化はしない（D-2 の3点目と同じ理由）。

- 判定はパス拡張子のみ。内容スニッフィングは行わない（FR-02 AC3）。既存の `FilePreviewKindResolver.sniffLooksLikeText` `[実コード: Sources/Panels/FilePreviewPanel.swift:883-895]` は「テキストかどうか」の判定であって言語判定ではなく、混同しない
- 表にない拡張子・拡張子なしは `.skippedNoLanguage` を返し、ハイライトを一切適用しない（FR-02 AC2）。**iOS 側にある「自動言語検出」フォールバック `[実コード: .../ChatArtifactSyntaxHighlightPolicy.swift:75-77]` は採らない**。FR-02 AC3 が拡張子のみと定めているため
- `.md` は `FileRouteSettingsStore.isMarkdownPath` `[実コード: Packages/macOS/CmuxSettings/Sources/CmuxSettings/Stores/FileRouteSettingsStore.swift:98-101]` により通常 Markdown パネルへ行くが、`MarkdownPanel` の TextEdit モードでもハイライトは効かせる（`MarkdownPanelView:94-104` の呼び出しに同じ引数を渡すため自動的にそうなる）

### 7.3 非同期化と可視範囲優先（NFR-04）

**`Highlightr` 同梱の `CodeAttributedString`（`NSTextStorage` サブクラス）は使わない。** 理由は2つ。(a) `makeFilePreviewTextView()` は `NSTextStorage()` を明示的に作って TextKit 1 スタックを組んでおり `[実コード: Sources/Panels/FilePreviewTextEditor.swift:157-168]`、ここを差し替えると P-2 の不変条件を検証しているテスト `[実コード: cmuxTests/FilePreviewTextEditorTextKitTests.swift:42]` の意図を壊す。(b) `NSTextStorage.processEditing` に同期ハイライトを載せる形になり、NFR-04 AC1（メインスレッド同期実行の禁止）に直接違反する。

**採る形**

```
FilePreviewSyntaxHighlightController (@MainActor)
  ├─ 可視範囲の算出（メインスレッド、O(可視行数)）
  │    layoutManager.glyphRange(forBoundingRect: clipView.documentVisibleRect, in: textContainer)
  │    → layoutManager.characterRange(forGlyphRange:actualGlyphRange:)
  │    → 前後にオーバースキャン行を足した NSRange
  ├─ その範囲の String スライスを actor へ渡す（値のコピー、Sendable）
  ├─ actor 側（メインアクター外・直列）でエンジンを回す
  └─ 戻ってきた [FilePreviewHighlightRun] を @MainActor で NSTextStorage へ適用
```

- **エンジンは `actor` に閉じてメインアクター外で直列化する。** iOS 側の `ChatArtifactSyntaxHighlighter` がまさにこの形（`actor` + 遅延生成した engine を保持）`[実コード: .../ChatArtifactSyntaxHighlighter.swift:5-21]`。`DispatchQueue` は使わない `[規約: skills/cmux-architecture/SKILL.md:106]`
- **NFR-03（未使用時ゼロ負荷）**: `attach` はハイライト有効かつ `previewMode == .text` のときだけコントローラを生成する。actor 内の engine も `ChatArtifactSyntaxHighlighter` と同じく初回 `runs(for:)` まで生成しない `[実コード: 同 :14-21]`
- **デバウンス**: `textDidChange` からの再計算は `Task` + `Clock.sleep` で 1 回にまとめる。`DispatchQueue.asyncAfter` は禁止 `[規約: skills/cmux-architecture/SKILL.md:107]`。前の `Task` は `cancel()` する。デバウンス幅は `[設計判断]`（初期値の根拠がないため未確定-08 へ）
- **スクロール追従**: `NSView.boundsDidChangeNotification`（`clipView.postsBoundsChangedNotifications = true`）を `NotificationCenter.default.notifications(named:)` で受ける `[規約: skills/cmux-architecture/SKILL.md:102（KVO ではなく NotificationCenter）]`
- **適用**: `textStorage.beginEditing()` → `removeAttribute(.foregroundColor, range:)` → ラン単位 `addAttribute(.foregroundColor, value:range:)` → `endEditing()`。範囲は必ず可視オーバースキャン範囲にクリップする
- **世代管理**: `FilePreviewPanel.saveTextContent` が `saveGeneration` で古い保存完了を捨てている `[実コード: Sources/Panels/FilePreviewPanel.swift:1313-1323]` のと同じく、コントローラも `highlightGeneration` を持ち、戻ってきた結果の世代が現行と違えば破棄する。テキストが入れ替わった後に古いランを適用して色がずれる事故を防ぐ

**Undo への影響**: 属性のみの変更は `NSTextView.shouldChangeText(in:replacementString:)` を経由しないため Undo スタックに乗らない、というのが本設計の前提である。これは `[設計判断]`（AppKit の挙動を実コードで確認したわけではない）。§16 に「ハイライト適用後に Undo が編集操作1回ぶん戻る」ことを確認するテストを必須項目として置く。

### 7.4 テーマ連動（FR-11）と `applyTheme` の衝突

**これは実装上の最大の落とし穴である。**

`FilePreviewTextEditor.applyTheme(to:backgroundColor:foregroundColor:drawsBackground:)` は `textView.textColor = foregroundColor` を実行する `[実コード: Sources/Panels/FilePreviewTextEditor.swift:109]`。`NSTextView.textColor` の setter はテキスト全体に `.foregroundColor` を適用する。そして `applyTheme` は `makeNSView` だけでなく **`updateNSView` の冒頭でも毎回呼ばれる** `[実コード: 同 :61-66]`。SwiftUI の更新が走るたびにハイライト色が本文色で塗り潰される。

**対処**: `applyTheme` に `preservesTextColor: Bool` を足し、ハイライト有効時は `textView.textColor` の一括代入を行わず、代わりに

- `textView.typingAttributes[.foregroundColor] = foregroundColor`（新規入力の色）
- 既定色は `FilePreviewHighlightPalette` の `plain` ロールとして、ハイライト適用時に `.plain` ランで塗る

とする。`insertionPointColor` は従来どおり設定する `[実コード: 同 :110]`。

`updateNSView` で `themeBackgroundColor` / `themeForegroundColor` が変わったときは `highlightController.setPalette(_:)` → `invalidateAll()` を呼ぶ。これで FR-11 AC2（再起動なしでテーマ追従）を満たす。

ハイライトが適用されない箇所（FR-02 フォールバック / FR-03 閾値超過 / 設定オフ）では `preservesTextColor = false` に戻し、`applyTheme` の従来経路で `themeForegroundColor` が全体に効く（FR-11 AC3）。

### 7.5 サイズ上限（FR-03）

- `FilePreviewTextLoader.maximumLoadedTextBytes = 16 * 1024 * 1024` と `:922-926` のサイズガードは**変更しない** `[実コード: Sources/Panels/FilePreviewPanel.swift:906, 922-926]`（NFR-05 AC1）

## 8. 行番号表示の設計（FR-05 / FR-06）

### 8.1 設置

```swift

scrollView.rulersVisible = lineNumbers
let ruler = FilePreviewLineNumberRulerView(scrollView: scrollView, orientation: .verticalRuler)

```

`updateNSView` では `scrollView.rulersVisible = lineNumbers` を都度代入するだけで live 反映になる（FR-06 AC1）。設定オフのときルーラは描画されない（NFR-14 AC2 / NFR-03 AC2）。

### 8.2 論理行の解決（FR-05 AC2）

`drawHashMarksAndLabels(in:)` の中で、

1. `layoutManager.glyphRange(forBoundingRect: textView.visibleRect, in: textContainer)`
2. `layoutManager.characterRange(forGlyphRange:actualGlyphRange:)`
3. `layoutManager.enumerateLineFragments(forGlyphRange:)` で **表示行**（line fragment）を走査
4. 各 fragment の先頭文字オフセットが `FilePreviewLineIndex.isLineStart(utf16Offset:)` を満たすときだけ番号を描く

これにより `fileEditor.wordWrap == true` で折り返された2行目以降には番号が出ない（FR-05 AC2）。ワードラップの切替は `applyFilePreviewWordWrap(_:scrollView:)` `[実コード: Sources/Panels/FilePreviewTextEditor.swift:194-218]` が担い、切替後に `ruler.needsDisplay = true` を打つ。

### 8.3 `FilePreviewLineIndex` が必要な理由

「文字オフセット → 論理行番号」を毎回テキスト先頭から数えると 16 MB / 数十万行のファイルで描画1回ごとに O(N) になる。`allowsNonContiguousLayout = true` で遅延レイアウトを成立させている設計 `[実コード: 同 :160]` の意図を打ち消す。

したがって行頭オフセットの配列を1本持ち、二分探索する。

- 初回構築: `textContent` 読み込み完了時に一度だけ。メインアクター外の `Task` で組み、`@MainActor` へ戻して差し替える
- 更新: `NSTextStorage` の `didProcessEditing` 相当のタイミングで `patched(editedRange:changeInLength:text:)`。編集位置より前は不変、後ろは `changeInLength` シフト、編集範囲内だけ再スキャンする
- メモリ: 50万行で `[Int]` 約 4 MB。`FilePreviewTextLoader` の 16 MB 上限 `[実コード: Sources/Panels/FilePreviewPanel.swift:906]` の内側なので許容範囲 `[設計判断]`
- 純 Foundation の値型なので AppKit なしで単体テスト可能（§16）

### 8.4 フォントズームとの同期（FR-05 AC3）

フォントは3経路で変わる。

| 経路 | 実コード |
|---|---|
| ピンチ | `magnify(with:)` `[実コード: Sources/Panels/FilePreviewTextEditor.swift:293-297]` |

`FilePreviewTextEditor.applyTheme` は `updateNSView` から毎回呼ばれ、`textView.textColor` にテーマ色を代入する `[実コード: Sources/Panels/FilePreviewTextEditor.swift:61-66, 109]`。§7.4 では `preservesTextColor` フラグを足す案を採ったが、これは既存の static メソッドのシグネチャを変える。呼び出しは同ファイル内2箇所だけなので影響は閉じるが、upstream が同メソッドを触っていた場合コンフリクトする。

**選択肢**: (a) 引数を足す、(b) ハイライト適用後に毎回 `applyTheme` の副作用を打ち消す（無駄な再描画が入る）、(c) `applyTheme` を呼ぶ前にハイライト有効かを判定して呼び分ける。本書は (a) を仮採用した `[設計判断]`。

### 新規-B 属性のみの変更が Undo に乗らないことの確認

§7.3 の前提（`textStorage` への属性追加は `NSTextView` の Undo に登録されない）は AppKit の挙動に依存し、実コードで確認していない `[設計判断]`。実装の最初のステップでこれを確認するテストを書き、成り立たなければ設計を見直す（`textView.shouldChangeText` を通さない別経路、または `undoManager.disableUndoRegistration()` で囲う）。

### 新規-C `FilePreviewLineIndex` の増分更新をどこで受けるか

`NSTextStorage` の編集通知（`didProcessEditing` / `NSTextStorageDelegate`）を使うか、`Coordinator.textDidChange` `[実コード: Sources/Panels/FilePreviewTextEditor.swift:124-128]` で全再構築するかが未決。前者は `editedRange` / `changeInLength` が取れて効率がよいが、`SavingTextView` に delegate を1つ足すことになる（§7.1 で「フィールドを追加しない」と決めた方針と緊張する）。後者は大きなファイルで毎キーストローク O(N) になる。`[設計判断]` としては前者だが、実装時に再評価する。

### 新規-D Compare は一時ファイルの書き出しを伴う

§9.4 のとおり、既存 Diff Viewer はローカルファイル URL の allowlist しか受け取れない `[実コード: Packages/macOS/CmuxBrowser/Sources/CmuxBrowser/DiffViewer/CmuxDiffViewerRegisteredFile.swift:4-15]`。Compare を実現するには未保存バッファを一時ファイルへ書き出す必要があり、(a) 書き出し先とライフサイクル（削除タイミング）、(b) マニフェスト生成側 `Native/DiffSidecar` の契約 `[要調査]`、(c) 一時ファイルに機微な内容が残るリスク、を決める必要がある。**要件定義の未確定-03 に (a)(b)(c) を追加する。**

### 新規-E 行番号を渡せるのは `PreferredEditorService` 経路のみ

§10.2 のとおり、`FileExternalOpenAction` は LaunchServices を使うため引数の口が構造的に無い `[実コード: Sources/Panels/FilePreviewPanel.swift:115-121]`。`PreferredEditorService` は `/bin/sh -c` で任意コマンドを起動するため口がある `[実コード: PreferredEditorService.swift:72-74]`。

したがって未確定-04 は「どのアプリに対応するか」ではなく **「行番号は `app.preferredEditor` コマンドにしか渡せない。それを FR-09 の答えとしてよいか」** に具体化される。よいとする場合、`app.preferredEditor` の値にプレースホルダ（`{file}` / `{line}`）を導入するか、既知コマンド名から形式を推定するかがさらに未決。

### 新規-F Settings 行の置き場所は「App セクション」である

`fileEditor.*` は専用セクションを持たず、`AppSection.swift` の Markdown Viewer Font と iMessage Mode の間にレンダリングされている `[実コード: Packages/macOS/CmuxSettingsUI/Sources/CmuxSettingsUI/Sections/AppSection.swift:503-514]`。ハイライトと行番号を「File Editor」という独立セクションに分けるかは未決。分ける場合、`CmuxSettingsUI` への差分が大きくなり NFR-08 に不利。**本書は既存どおり App セクションへ追加する前提で書いた** `[設計判断]`。

### 20.2 技術的実現性

- 最大のリスクは **ハイライトエンジンが可視範囲だけの入力を正しく扱えるか**（§5 D-2 の performance 軸）。ブロックコメント・複数行文字列がスライス境界で壊れる可能性がある。緩和策はオーバースキャンだが完全ではない
- 次のリスクは **`FilePreviewLineIndex` の増分更新**（新規-C）。全再構築に倒せば正しいが遅い。テストで全再構築との一致を保証する設計にした
- `NSRulerView` はリポジトリに先例がなく `[設計判断]` の比重が高い。ただし AppKit の標準機能であり、失敗しても代替案（§5 D-3 の2番目）に退避できる

### 20.3 拡張性

- `FilePreviewSyntaxHighlighting` の seam により、エンジンを差し替えても `FilePreviewSyntaxHighlightController` 以降は不変（§5 D-2）
- `FilePreviewTokenRole` を意味論で切ったことで、テーマ追加はパレット1枚の追加で済む（FR-11）
- `FilePreviewLineIndex` は行番号以外（FR-09 のカーソル行、将来の折りたたみ）にも使える
- 一方、**LSP（REQ-25）や Live Diff（REQ-24）への橋渡しは意図的に設けていない**。MVP 対象外であり、投機的な抽象化は入れない

### 20.4 運用性（upstream 追従とデバッグ容易性）

- §18 で差分の局所化状況を明示。新規15ファイルは upstream と衝突しえない
- デバッグ: `#if DEBUG` で `cmuxDebugLog("...")` を使える `[規約: skills/cmux-debugging/SKILL.md:「Debug event log」]`。ハイライトの世代破棄・可視範囲の変化はここに出す候補だが、恒久的なログは入れない（同スキルが「大半のプローブは dogfood 用で merge 前に消す」としている）
- 設定は `cmux.json` で切れるため、不具合時にユーザー側で無効化できる（FR-04 / FR-06 の運用上の意義）

### 20.5 セキュリティ（ファイルアクセス権限とサンドボックス）

- アプリはサンドボックス化されていない（`com.apple.security.app-sandbox` はどの entitlements にも存在しない）。したがってファイルアクセスに新しい権限要求は発生しない
- 配布ビルドは `allow-jit` / `allow-unsigned-executable-memory` / `disable-library-validation` を持つ `[実コード: cmux.entitlements:5-10]`。Highlightr（JavaScriptCore）を入れても新しい entitlement は不要
- **注意点**: ハイライトはファイル内容を JavaScriptCore に渡すことになる。ローカル完結でありネットワークに出ないが、highlight.js は第三者コードである。`[設計判断]` として、エンジンを自前実装に倒せばこの面は消える（未確定-02 の評価軸に「第三者コードにファイル内容を渡すこと」を追加すべき）
- **新規-D（Compare の一時ファイル）は明確なセキュリティ論点**である。未保存の機微な内容が一時ファイルとしてディスクに残る。未確定-03 の決定時に必ず扱う
- 保存衝突 UI は既存の保存経路（`FilePreviewTextSaver.save` `[実コード: Sources/Panels/FilePreviewPanel.swift:959-971]`）を変えないため、書き込み権限まわりの挙動は不変
