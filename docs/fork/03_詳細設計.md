## 1. Why

cmux の File Preview / Markdown パネルは既に編集可能なテキストエディタである（編集・Undo・Find・保存・外部変更検知が実装済み）`[実コード: Sources/Panels/FilePreviewTextEditor.swift:171-176, Sources/Panels/FilePreviewPanel.swift:1301-1339]`。エージェントの出力を読むために外部エディタへ出る必要がなくなる最後の2要素が **シンタックスハイライト** と **行番号** である。

この2つは「新しいエディタを作る」話ではない。既存の `SavingTextView`（明示的に構築された TextKit 1 スタック）に、属性付与とルーラ描画を **足す** 話である。本書の価値は「既存コードのどこをどう触るか」を確定させることにあり、新規アーキテクチャの提案ではない。

## 2. 設計方針

### 2.1 5つの原則

| # | 原則 | 根拠 |
|---|---|---|
| P-1 | **新しい `PanelType` を作らない。既存 `.filePreview` / `.markdown` を拡張する** | §5 D-1 |
| P-2 | **`SavingTextView` の TextKit 1 構築を1行も崩さない**（`textLayoutManager == nil` を保つ） | NFR-07 / `[実コード: cmuxTests/FilePreviewTextEditorTextKitTests.swift:42]` |
| P-3 | **ハイライトエンジンを具体ライブラリに直結させず、値型の seam を1枚挟む**（未確定-02 を実装開始のブロッカーにしない） | NFR-11 / §5 D-2 |
| P-4 | **複数入口を持つ振る舞いは共有アクション1本に集約する**（分岐を各入口へ足さない） | `[規約: AGENTS.md:103-105, skills/cmux-shared-behavior/SKILL.md「Shared entrypoints」]` |
| P-5 | **差分の中心を `Sources/Panels/` / `Packages/macOS/CmuxSettings*` / `web/` / `docs/fork/` に置く。はみ出す分は §18.4 に列挙して理由を残す** | NFR-08 / 02 NFR-08 AC4 |

> P-5 は「はみ出さない」ではなく「はみ出しを隠さない」原則である。§4.1 の時点で設定キー1本の登録先が app target 側の6ファイルに散っており（§12.2）、FR-09 は下位パッケージ `CmuxWorkspaces` に触れる（§10.2）。実態と逸脱理由は §18.4 に集約する。02 NFR-08 AC4 が「収まらない場合は理由を `docs/fork/` に記録する」と定めているため、この記録自体が受け入れ条件の充足になる。

### 2.2 P-5 に伴う意図的な逸脱（1件）

`skills/cmux-architecture/SKILL.md:10-16` は新しいドメインを Swift Package として切り出すことを求める。しかし新規パッケージの追加は `cmux` と `cmux-unit` の **両ターゲット** に pbxproj エントリを要し `[規約: skills/cmux-architecture/SKILL.md:18]`（`cmux-unit` は scheme 名であり、pbxproj 上の実ターゲット名は `cmuxTests` `[実コード: cmux.xcodeproj/project.pbxproj:8639, cmux.xcodeproj/xcshareddata/xcschemes/cmux-unit.xcscheme]`）、さらに `cmux.xcworkspace/contents.xcworkspacedata` のグループ更新（`python3 scripts/check-workspace-package-groups.py --write`）を伴う `[規約: skills/cmux-architecture/SKILL.md:20]`。これは fork の差分を upstream の中枢ファイルへ広げる。

本書では **新規パッケージを作らず**、新規型は `Sources/Panels/` 配下の app-target ファイルとして追加する。同スキル自身が「境界が存在するのは複数の consumer が必要とするとき」としており `[規約: skills/cmux-architecture/SKILL.md:14]`、本設計の新規型の consumer は `FilePreviewTextEditor` 系のみで、この条件を満たさない。ただし app-target 新規ファイルにも **1ファイル1型 / 自由関数禁止 / DocC** は適用する `[規約: skills/cmux-architecture/SKILL.md:54-59, 80, 63]`。

## 5. 主要な設計判断

### D-1 【最上位・未確定-01 への回答】Panel 層に足す。新しい `PanelType` は追加しない

**結論**: `FilePreviewPanel` / `MarkdownPanel`（Panel 層）の拡張として実装する。`PanelType` にも `CmuxSurfaceType` にもケースを追加しない。

**根拠1: `CmuxSurfaceType` は Session Restore と無関係**

`CmuxSurfaceType` の参照はリポジトリ全体で `Sources/CmuxConfig.swift` の2行のみ `[実コード: Sources/CmuxConfig.swift:1611, 1620]`（`grep -rn "CmuxSurfaceType" --include="*.swift" .` の全件）。設定ファイルの宣言的レイアウトスキーマであり、復元経路には現れない。01 §6 訂正の前提は実コードと一致しない（要件定義 §0 で既に指摘済み）。

**根拠2: 新 `PanelType` ケースは fork にとって片道切符になる**

`PanelType.init(from:)` は未知の raw value に対して `DecodingError.dataCorruptedError` を **throw する** `[実コード: Sources/Panels/Panel.swift:66-69]`。そして `SessionWorkspaceSnapshot.panels` は `[SessionPanelSnapshot]`（Optional ではない）で合成 `Codable` を使う `[実コード: Sources/SessionPersistence.swift:1839]`。したがって1つのパネルの type が読めないだけで **workspace snapshot 全体のデコードが失敗する**。

### D-4 保存衝突 UI は「シートではなくパネル内バナー」

**結論**: `NSAlert` のモーダルシートではなく、パネルヘッダ直下に条件付きで現れる SwiftUI バナーにする。

**理由**

- NFR-14 は「常時表示 UI を増やさない」であって、条件付き UI を禁じてはいない。バナーは `isDirty && 衝突あり` のときだけ現れる
- モーダルシートはウィンドウ全体を止める。cmux は複数のエージェントセッションが同時に走る前提のアプリであり、1ファイルの衝突で他ペインの操作を止めるのは思想に反する `[メモ由来: REQ-01 / 要件定義 §0]`
- 「選択を出している間にさらに外部変更が起きてもバッファが失われない」（FR-07 AC5）は、モーダルより非モーダルのほうが素直に書ける

**ただしテスト容易性は `NSAlert` 経路の先例に倣う**。`BrowserHTTPBasicAuthPrompt` は `alertFactory` と `presentAlert: BrowserAlertPresenter` を引数で注入し、テストが実際のダイアログを出さずに検証できるようにしている `[実コード: Sources/Panels/BrowserHTTPBasicAuthPrompt.swift:52-58, Sources/Panels/BrowserPanel.swift:1059-1078]`。本設計でも解決の適用を `FilePreviewSaveConflictCoordinator` に閉じ、View 抜きで単体テストできる形にする。

衝突の重複統合は `BrowserHTTPBasicAuthPromptCoordinator` の形を参考にする。同クラスは同一 protection space の要求を1件にまとめ、キュー長に上限を持つ `[実コード: Sources/Panels/BrowserHTTPBasicAuthPromptCoordinator.swift:14-15, 38-48]`。本設計は「1パネル = 1ファイル」なので**キューではなく最新の1件で上書き**する（§9.2）。

### D-5 設定アクセサは既存 `FilePreviewWordWrapSettings` に形を揃える

`skills/cmux-architecture/SKILL.md:77` は namespace-enum（`enum Foo { static func bar() }`）の新設を禁じている。しかし `fileEditor.*` の既存アクセサ `FilePreviewWordWrapSettings` はまさにその形であり `[実コード: Sources/Panels/FilePreviewWordWrapSettings.swift:9-21]`、`@AppStorage(FilePreviewWordWrapSettings.key)` として2つの View から使われている `[実コード: Sources/Panels/FilePreviewPanel.swift:1381, Sources/Panels/MarkdownPanelView.swift:32]`。

**理由**: `@AppStorage` は `key: String` と `defaultValue` の静的な組を必要とし、インスタンスを注入できない。ここだけ別の形にすると `fileEditor.*` の3キーが2種類の書き方に割れ、次に触る人が判断できなくなる。スキル自身も「既存 app-target コードを盲目的に retrofit するな」としている `[規約: skills/cmux-architecture/SKILL.md:124]`。

一方、**判定ロジックを持つ新規型（`FilePreviewHighlightPolicy` など）は namespace-enum にしない**。`struct` にして `UserDefaults` や閾値を `init` で受け取り、テストから注入できるようにする `[規約: skills/cmux-architecture/SKILL.md:84-88]`。

## 6. Model（新規型）

すべて値型または `@MainActor` クラス。AppKit 依存を持つのは `FilePreviewHighlightPalette`（`NSColor`）と `FilePreviewLineNumberRulerView`、`FilePreviewSyntaxHighlightController` のみ。

```swift
// 色を持たない意味論トークン。エンジンとテーマを分離する要。
enum FilePreviewTokenRole: Sendable { case keyword, string, comment, number, type, attribute, plain }

struct FilePreviewHighlightRun: Sendable, Equatable {
    let range: NSRange
    let role: FilePreviewTokenRole
}

protocol FilePreviewSyntaxHighlighting: Sendable {
    /// 座標系の契約（実装・呼び出しの両方がこれに従う）:
    /// - `text` は **ドキュメント全文**。スライスを渡してはならない
    ///   （`String` は COW なので値渡しのコピーコストは無い）
    /// - `range` は **全文の UTF-16 座標**で表した「今すぐ色が要る範囲」
    /// - 戻り値の `FilePreviewHighlightRun.range` も **全文の UTF-16 座標**
    /// - `range` に交差するトークンだけを返せばよい。範囲外を返してもよく、
    ///   呼び出し側が `range` でクリップする
    ///
    /// 全文を渡すのは、ブロックコメントや複数行文字列の開始が `range` より
    /// 手前にあっても正しく解釈させるためである（§20.2 の最大リスク）。
    func runs(for text: String, language: String, range: NSRange) async -> [FilePreviewHighlightRun]
}

/// 保存衝突の解決でコーディネータがパネルへ要求する最小契約。
/// 既存の `FilePreviewTextEditingPanel` には**足さない**（§20.7）。
/// `loadTextContent(replacingDirtyContent:)` の戻り値型が2実装で異なる
/// （`FilePreviewPanel` は `Task<Void, Never>` `[実コード: Sources/Panels/FilePreviewPanel.swift:1255]`、
/// `MarkdownPanel` は `Task<Void, Never>?` `[実コード: Sources/Panels/MarkdownPanel.swift:301]`）ため、
/// 戻り値を持たない別名のメソッドを要求し、各実装が自分の既存 API へ委譲する。
@MainActor
protocol FilePreviewSaveConflictResolving: AnyObject {
    var isDirty: Bool { get }                 // 既存 @Published private(set) var で充足
    func reloadDiscardingLocalEdits()         // 実装は loadTextContent(replacingDirtyContent: true) を呼ぶだけ
}

enum FilePreviewHighlightDecision: Sendable, Equatable {
    case highlight(language: String)
    case skippedForSize
    case skippedNoLanguage
}

struct FilePreviewHighlightPolicy: Sendable {
    let maximumHighlightBytes: Int
    let languages: FilePreviewSyntaxLanguage
    func decision(path: String, byteCount: Int) -> FilePreviewHighlightDecision
}

/// 論理行の開始オフセット（UTF-16）。二分探索で行番号を引く。
/// シフトは配列を書き換えず「境界より後ろへ一律に加える保留量」として持つ（§8.3）。
struct FilePreviewLineIndex: Sendable, Equatable {
    private let lineStarts: [Int]        // 保留シフト適用前の値
    private let shiftBoundary: Int       // この添字以降に pendingShift を加える
    private let pendingShift: Int
    /// このインデックスがどのテキスト世代から作られたか。§7.3 のハイライト世代と同じ役割。
    let generation: Int
    init(text: NSString, generation: Int)
    var lineCount: Int
    func lineNumber(atUTF16Offset offset: Int) -> Int      // 1 始まり
    func isLineStart(utf16Offset: Int) -> Bool
    /// 編集後の増分更新。編集範囲より前は不変、後ろは `pendingShift` に加算するだけ
    /// （配列の再構築をしない）。編集範囲内の行頭のみ再スキャンして差し替える。
    func patched(editedRange: NSRange, changeInLength: Int, text: NSString) -> FilePreviewLineIndex
}

struct FilePreviewSaveConflict: Sendable, Equatable {
    let filePath: String
    let diskContent: String
    let detectedAt: Date
}

enum FilePreviewSaveConflictResolution: Sendable, Equatable { case reload, compare, keepMine }

struct FilePreviewExternalOpenLocation: Sendable, Equatable {
    let fileURL: URL
    let line: Int?     // 1 始まり。nil は行指定なし（従来挙動）
}
```

## 7. シンタックスハイライトの設計（FR-01 / FR-02 / FR-03 / FR-11）

### 7.1 差し込み位置

現状のテキスト構築経路は次の3点である。

1. `FilePreviewTextEditor.makeNSView(context:)` — `SavingTextView.makeFilePreviewTextView()` を作り `textView.string = panel.textContent` を代入 `[実コード: Sources/Panels/FilePreviewTextEditor.swift:40-47]`
2. `FilePreviewTextEditor.updateNSView(_:context:)` — `textView.string != panel.textContent` のとき、選択範囲とスクロール位置を保存しつつ `textView.string` を差し替える `[実コード: 同 :72-92]`
3. `Coordinator.textDidChange(_:)` — ユーザー入力を `panel.updateTextContent(textView.string)` へ流す `[実コード: 同 :124-128]`

**`textView.string` への代入は `NSTextStorage` の属性を全消去する。** したがってハイライトの再適用トリガはこの3点＋テーマ変更＋フォント変更である。

差し込みは `Coordinator` に `FilePreviewSyntaxHighlightController` を1つ持たせる形にする。`Coordinator` は既に `NSTextViewDelegate` であり `panel` の参照を持つ `[実コード: 同 :114-121]`。

```
  └─ syntaxHighlight == true のとき
       coordinator.highlightController = FilePreviewSyntaxHighlightController(policy:palette:)
       controller.attach(textView:scrollView:)          // 購読 Task の開始もここ（§7.3）
       ※ この時点の panel.textContent は空文字のことがある（下記）。サイズ判定はここでは行わない
FilePreviewTextEditor.updateNSView
  ├─ coordinator.highlightController?.setEnabled(syntaxHighlight)                  // 設定のライブ反映（FR-04 AC1）
  ├─ coordinator.highlightController?.setPalette(FilePreviewHighlightPalette(background: themeBackgroundColor, foreground: themeForegroundColor))
  └─ textView.string 差し替えの直後に
       coordinator.highlightController?.noteDocumentReplaced(text: textView.string)  // ここでサイズ・言語を判定（§7.5）→ invalidateAll()
Coordinator.textDidChange
  └─ coordinator.highlightController?.noteTextDidChange()                          // デバウンス開始
```

### 7.3 非同期化と可視範囲優先（NFR-04）

**`Highlightr` 同梱の `CodeAttributedString`（`NSTextStorage` サブクラス）は使わない。** 理由は2つ。(a) `makeFilePreviewTextView()` は `NSTextStorage()` を明示的に作って TextKit 1 スタックを組んでおり `[実コード: Sources/Panels/FilePreviewTextEditor.swift:157-168]`、ここを差し替えると P-2 の不変条件を検証しているテスト `[実コード: cmuxTests/FilePreviewTextEditorTextKitTests.swift:42]` の意図を壊す。(b) `NSTextStorage.processEditing` に同期ハイライトを載せる形になり、NFR-04 AC1（メインスレッド同期実行の禁止）に直接違反する。

**採る形**

```
FilePreviewSyntaxHighlightController (@MainActor)
  ├─ 可視範囲の算出（メインスレッド、O(可視行数)）
  │    layoutManager.glyphRange(forBoundingRect: clipView.documentVisibleRect, in: textContainer)
  │    → layoutManager.characterRange(forGlyphRange:actualGlyphRange:)
  │    → 前後にオーバースキャン行を足した NSRange
  ├─ 全文の String と その NSRange を actor へ渡す（スライスにしない。§6 の座標契約）
  ├─ actor 側（メインアクター外・直列）でエンジンを回す
  └─ 戻ってきた [FilePreviewHighlightRun]（全文座標）を @MainActor で NSTextStorage へ適用
```

**渡すのは全文であって可視範囲のスライスではない。** §6 の `FilePreviewSyntaxHighlighting` のドキュメントコメントがこの契約の正本である。`text` = 全文 / `range` = 全文座標 / 戻り値 = 全文座標で統一する。理由は2つ。(a) スライスを渡すと `range` の基準がスライス先頭になり、取り違えた実装が**全く違う位置に属性を付ける**。(b) ブロックコメント・複数行文字列の開始が可視範囲より手前にあるとき、スライスでは正しく解釈できない（§20.2 の最大リスク）。`String` は COW なので全文を値渡ししてもコピーは発生しない。「可視範囲優先」（NFR-04）は **`range` を可視範囲に絞ること**で満たす。

- **エンジンは `actor` に閉じてメインアクター外で直列化する。** iOS 側の `ChatArtifactSyntaxHighlighter` がまさにこの形（`actor` + 遅延生成した engine を保持）`[実コード: .../ChatArtifactSyntaxHighlighter.swift:5-21]`。`DispatchQueue` は使わない `[規約: skills/cmux-architecture/SKILL.md:106]`
- **NFR-03（未使用時ゼロ負荷）**: コントローラは **`syntaxHighlight` 設定がオンのときだけ**生成する。「テキストモードであること」は条件に書かない — `FilePreviewTextEditor` が生成される時点で既にテキストモードだからである（`FilePreviewPanelView.content` の `switch panel.previewMode` の `.text` 枝 `[実コード: Sources/Panels/FilePreviewPanel.swift:1451-1460]` と、`MarkdownPanelView.markdownBody` の `if panel.displayMode == .text` 枝 `[実コード: Sources/Panels/MarkdownPanelView.swift:94-102]` でのみ生成される）。**`previewMode` を attach 地点で読むことはできない**: attach 地点は `FilePreviewTextEditor` であり、その `panel` は `FilePreviewTextEditingPanel` `[実コード: Sources/Panels/FilePreviewTextEditor.swift:7-15]` で `previewMode` を持たない。`MarkdownPanel` 側にあるのは `displayMode: MarkdownPanelDisplayMode` という別のプロパティである `[実コード: Sources/Panels/MarkdownPanel.swift:40]`。actor 内の engine も `ChatArtifactSyntaxHighlighter` と同じく初回 `runs(for:)` まで生成しない `[実コード: 同 :14-21]`
- **デバウンス**: `textDidChange` からの再計算は `Task` + `Clock.sleep` で 1 回にまとめる。`DispatchQueue.asyncAfter` は禁止 `[規約: skills/cmux-architecture/SKILL.md:107]`。前の `Task` は `cancel()` する。デバウンス幅は `[設計判断]`（初期値の根拠がないため未確定-08 へ）
- **スクロール追従**: `NSView.boundsDidChangeNotification`（`clipView.postsBoundsChangedNotifications = true`）を `NotificationCenter.default.notifications(named: NSView.boundsDidChangeNotification, object: clipView)` で受ける `[規約: skills/cmux-architecture/SKILL.md:102（KVO ではなく NotificationCenter）]`。**`object:` に自分の `NSClipView` を必ず渡す**。省くとアプリ内の全 `NSView` の bounds 変更（ターミナルを含む）で発火し、§7.7 の「購読するのは自分の `NSClipView` だけ」が破れる
- **購読 Task のライフサイクル**: `for await` ループは自分自身を生かし続けるため、`attach` で作った Task を `subscriptionTask` として保持し、`detach()`（`dismantleNSView` / パネル close）で必ず `cancel()` する。ループ内では `[weak self]` で受け、`self` が nil なら `break` する（`FilePreviewPanel+Reload.swift` の監視 Task と同じ形 `[実コード: Sources/Panels/FilePreviewPanel+Reload.swift:13-18]`）。これを怠るとパネルを閉じても `NSTextView` / `NSScrollView` ごとリークする
- **適用**: `textStorage.beginEditing()` → `removeAttribute(.foregroundColor, range:)` → ラン単位 `addAttribute(.foregroundColor, value:range:)` → `endEditing()`。**適用直前に `NSIntersectionRange(range, NSRange(location: 0, length: textStorage.length))` でクランプする。** クリップ先は「計算時点の可視範囲」ではなく「適用時点の `textStorage.length`」でなければならない。世代チェックが漏れる経路が1つでもあると `NSRangeException` でクラッシュするため、クランプは世代管理とは独立の防御として置く
- **世代管理**: `FilePreviewPanel.saveTextContent` が `saveGeneration` で古い保存完了を捨てている `[実コード: Sources/Panels/FilePreviewPanel.swift:1313-1323]` のと同じく、コントローラも `highlightGeneration` を持ち、戻ってきた結果の世代が現行と違えば破棄する。テキストが入れ替わった後に古いランを適用して色がずれる事故を防ぐ。**契約: `invalidateAll()` / `noteDocumentReplaced(text:)` / `noteTextDidChange()` は必ず世代を加算する。** 世代を加算しない無効化経路を作らない

**Undo への影響**: 属性のみの変更は `NSTextView.shouldChangeText(in:replacementString:)` を経由しないため Undo スタックに乗らない、というのが本設計の前提である。これは `[設計判断]`（AppKit の挙動を実コードで確認したわけではない）。§16 に「ハイライト適用後に Undo が編集操作1回ぶん戻る」ことを確認するテストを必須項目として置く。

### 7.4 テーマ連動（FR-11）と `applyTheme` の衝突

**これは実装上の最大の落とし穴である。**

`FilePreviewTextEditor.applyTheme(to:backgroundColor:foregroundColor:drawsBackground:)` は `textView.textColor = foregroundColor` を実行する `[実コード: Sources/Panels/FilePreviewTextEditor.swift:109]`。`NSTextView.textColor` の setter はテキスト全体に `.foregroundColor` を適用する。そして `applyTheme` は `makeNSView` だけでなく **`updateNSView` の冒頭でも毎回呼ばれる** `[実コード: 同 :61-66]`。SwiftUI の更新が走るたびにハイライト色が本文色で塗り潰される。

**対処**: `applyTheme` に `preservesTextColor: Bool` を足し、ハイライト有効時は `textView.textColor` の一括代入を行わず、代わりに

- `textView.typingAttributes[.foregroundColor] = foregroundColor`（新規入力の色）
- **`invalidateAll()` の直後に、文書全体へ `FilePreviewHighlightPalette` の `.plain` 色を1回だけ `addAttribute(.foregroundColor:range: 全文)` する**。その上に可視範囲のハイライトを重ねる

とする。`insertionPointColor` は従来どおり設定する `[実コード: 同 :110]`。

**全文に既定色を敷く手順を省いてはならない（FR-11 AC3）。** ハイライトは可視範囲＋オーバースキャンしか塗らないため、`textView.textColor` の一括代入をやめただけでは、スクロールして初めて可視になった領域が `NSTextView` 既定色（黒）で描画される時間が生じる。暗背景テーマではその間まったく読めない。全文への単一属性適用は run が1本にまとまるため、16 MB でもコストは無視できる `[設計判断]`。§16.2 の `FilePreviewSyntaxHighlightControllerTests` に「可視範囲外の文字にも `.foregroundColor` が付いている」ケースを置いて回帰を止める。

`updateNSView` で `themeBackgroundColor` / `themeForegroundColor` が変わったときは `highlightController.setPalette(_:)` → `invalidateAll()` を呼ぶ。これで FR-11 AC2（再起動なしでテーマ追従）を満たす。

ハイライトが適用されない箇所（FR-02 フォールバック / FR-03 閾値超過 / 設定オフ）では `preservesTextColor = false` に戻し、`applyTheme` の従来経路で `themeForegroundColor` が全体に効く（FR-11 AC3）。

## 8. 行番号表示の設計（FR-05 / FR-06）

### 8.1 設置

```swift
// makeNSView 内、scrollView.documentView = textView の直後
scrollView.hasVerticalRuler = true
scrollView.rulersVisible = lineNumbers
let ruler = FilePreviewLineNumberRulerView(scrollView: scrollView, orientation: .verticalRuler)
ruler.clientView = textView
scrollView.verticalRulerView = ruler
```

`updateNSView` では `scrollView.rulersVisible = lineNumbers` を都度代入するだけで live 反映になる（FR-06 AC1）。設定オフのときルーラは描画されない（NFR-14 AC2 / NFR-03 AC2）。

### 8.2 論理行の解決（FR-05 AC2）

`drawHashMarksAndLabels(in:)` の中で、

1. `layoutManager.glyphRange(forBoundingRect: textView.visibleRect, in: textContainer)`
2. `layoutManager.characterRange(forGlyphRange:actualGlyphRange:)`
3. `layoutManager.enumerateLineFragments(forGlyphRange:)` で **表示行**（line fragment）を走査
4. 各 fragment の先頭文字オフセットが `FilePreviewLineIndex.isLineStart(utf16Offset:)` を満たすときだけ番号を描く

これにより `fileEditor.wordWrap == true` で折り返された2行目以降には番号が出ない（FR-05 AC2）。ワードラップの切替は `applyFilePreviewWordWrap(_:scrollView:)` `[実コード: Sources/Panels/FilePreviewTextEditor.swift:194-218]` が担い、切替後に `ruler.needsDisplay = true` を打つ。

### 8.3 `FilePreviewLineIndex` が必要な理由

「文字オフセット → 論理行番号」を毎回テキスト先頭から数えると 16 MB / 数十万行のファイルで描画1回ごとに O(N) になる。`allowsNonContiguousLayout = true` で遅延レイアウトを成立させている設計 `[実コード: 同 :160]` の意図を打ち消す。

したがって行頭オフセットの配列を1本持ち、二分探索する。

- 初回構築: `textContent` 読み込み完了時に一度だけ。メインアクター外の `Task` で組み、`@MainActor` へ戻して差し替える
- **世代管理（必須）**: 構築を非同期にする以上、ハイライト（§7.3）と同じ世代番号をインデックスにも持たせる。`@MainActor` へ戻して差し替える瞬間に `index.generation == currentTextGeneration` を検査し、不一致なら**捨てて組み直す**。これが無いと、構築中に編集が入ったとき古いインデックスで上書きされ **行番号が本文とずれる**（FR-05 AC1 違反）。ずれた行番号は見た目が正しそうに見えるため気づきにくく、テストで止めるしかない（§16.2）
- 更新: `NSTextStorage` の `didProcessEditing` 相当のタイミングで `patched(editedRange:changeInLength:text:)`
- **`patched` は配列を作り直さない。** 「編集位置より後ろを `changeInLength` だけシフトした新しい配列を作る」実装は、シフト対象が末尾までである以上 **1打鍵ごとに O(N) の書き込み**になる（50万行なら約 4 MB の `[Int]` を毎回生成し、値型なので COW も効かない）。代わりに `(shiftBoundary, pendingShift)` の組を1つだけ持ち、二分探索時に「添字が `shiftBoundary` 以上なら `pendingShift` を足す」形でシフトを**遅延**させる（§6 のシグネチャ）。連続編集で新しい境界が前回より後ろにあるときは、その2点の**間の要素だけ**を実値へ畳み込む（編集を跨いだ行数ぶんの O(k)）。境界が前へ戻ったときだけ全体を畳み込む（O(N)、稀）
- メモリ: 50万行で `[Int]` 約 4 MB。`FilePreviewTextLoader` の 16 MB 上限 `[実コード: Sources/Panels/FilePreviewPanel.swift:906]` の内側なので許容範囲 `[設計判断]`
- 純 Foundation の値型なので AppKit なしで単体テスト可能（§16）

### 8.4 フォントズームとの同期（FR-05 AC3）

フォントは3経路で変わる。

| 経路 | 実コード |
|---|---|
| ピンチ | `magnify(with:)` `[実コード: Sources/Panels/FilePreviewTextEditor.swift:293-297]` |
| 修飾キー + スクロール / スマートズーム | `scrollWheel(with:)` `[実コード: 同 :299-313]` |
| ショートカット（`browserZoomIn` / `Out` / `Reset`） | `performPreviewFontZoomShortcutAction(_:)` `[実コード: 同 :437-448]` |
| アプリ全体の拡大率変更 | `GlobalFontMagnificationChangeObserver` `[実コード: 同 :262-266, Packages/macOS/CmuxFoundation/Sources/CmuxFoundation/GlobalFontMagnificationChangeObserver.swift:9]` |

いずれも最終的に `applyCurrentPreviewFont()` `[実コード: Sources/Panels/FilePreviewTextEditor.swift:345-349]` に集まる。ここを **唯一の同期点** とし、ルーラのフォント更新・`ruleThickness` 再計算・再描画をこの1箇所から行う（P-4 の共有アクション原則の適用）。

ルーラのフォントは本文と同じ `GlobalFontMagnification.monospacedSystemFont(ofSize:weight:)` を使う `[実コード: 同 :346]`。番号の縦位置は line fragment の `rect` を `NSRulerView` の座標へ変換して合わせる。

### 8.5 桁数と幅（FR-05 AC5）

`ruleThickness = ceil(数字1文字幅 × max(3, 桁数(lineCount))) + 左右パディング`。`FilePreviewLineIndex.lineCount` が変わったときだけ再計算する。`ruleThickness` の変更は `NSScrollView` が本文の幅を自動的に詰めるため、本文が水平に切れることはない `[設計判断]`。

### 9.2 追加する層

#### 検知点は「再読込を止める場所」ではなく「既存の dirty 枝の中」

**`handleObservedFileChange()` に分岐を足す設計は採らない。** 理由は3つあり、いずれも実コードで確認した。

1. **`diskContent` の生成元が無い**。`handleObservedFileChange()` の時点ではまだディスクを読んでいない `[実コード: Sources/Panels/FilePreviewPanel+Reload.swift:22-31]`。ここで `FilePreviewSaveConflict` を組み立てるには `FilePreviewTextLoader` を別に回すことになり、「新しい読み込み経路は作らない」という本節の方針と衝突する
2. **`isDirty` で `reloadFromDisk()` を止めると既存の副作用が失われる**。dirty 枝の `originalTextContent = content` / `setTabMetadataDirtyState(textContent != originalTextContent)` / `isFileUnavailable = false` `[実コード: Sources/Panels/FilePreviewPanel.swift:1286-1292]` が走らなくなり、(a) タブの dirty 表示がディスク実体とずれる（NFR-06 の回帰）、(b) `isFileUnavailable` が更新されないため §20.8 の「ファイルが消えたら `fileUnavailableView` に切り替わる」緩和策が成立しなくなる
3. **`handleObservedFileChange()` の呼び出し点は2つではなく3つある**。監視ループ `[実コード: Sources/Panels/FilePreviewPanel+Reload.swift:16]` に加え、**保存失敗経路からも呼ばれる** `[実コード: Sources/Panels/FilePreviewPanel.swift:1335]`。保存失敗直後は `textContent` が新内容・`originalTextContent` が旧内容で `isDirty == true` になり得るため、ここに衝突分岐を置くと「外部変更が無いのに保存失敗で衝突バナーが出る」経路が生まれる

**採る形**: `reloadFromDisk()` は従来どおり走らせる。そのうえで、**既に dirty 枝に入ったときに**コーディネータへ通知する。ディスク側の内容 `content` はその枝で `originalTextContent` に入る値そのものなので、**追加の I/O は発生しない**。


### 9.4 Compare（FR-08）— 既存 Diff Viewer の適合性

本書で判明した事実:

- 既存 Diff Viewer は `cmux-diff-viewer` カスタムスキームを WebView に登録する方式 `[実コード: Sources/Panels/CmuxDiffViewerURLSchemeHandler.swift:10]`
- 配信対象は **トークンごとの allowlist に登録されたローカルファイル**である。`CmuxDiffViewerRegisteredFile` は `requestPath` / `fileURL` / `mimeType` / `fileSize` を持ち、**内容ではなくファイル URL を指す** `[実コード: Packages/macOS/CmuxBrowser/Sources/CmuxBrowser/DiffViewer/CmuxDiffViewerRegisteredFile.swift:4-15]`
- 実際の登録は `registerFromManifest(token:now:)` 経由で、**オンディスクのマニフェスト**（`Native/DiffSidecar` が書く）から読む `[実コード: Sources/Panels/CmuxDiffViewerURLSchemeHandler.swift:365-373, :12]`

加えて、受け取れるものには次の**強い制約**がある。

- **許可 MIME は3種だけ**: `text/html` / `text/javascript` / `text/x-diff` `[実コード: Packages/macOS/CmuxBrowser/Sources/CmuxBrowser/DiffViewer/CmuxDiffViewerSessionPreparer.swift:291-292]`。さらに拡張子が MIME と一致していなければ拒否される（`text/x-diff` は `.patch` のみ）`[実コード: 同 :295-306]`
- **置き場所は1箇所に固定されている**: 全登録ファイルは trusted root の**内側**でなければ `unreadableFile` で拒否される `[実コード: 同 :89-92, :225-227]`。root の既定値は `/tmp/cmux-diff-viewer-<uid>/` `[実コード: 同 :18-22]`。`NSTemporaryDirectory()` の下に書いても**受け付けられない**

**結論**: 「2ファイルを指すマニフェストを渡して Diff Viewer に差分を計算させる」方式は成立しない。成立する形は次の1つである。

> **アプリ側で unified diff を生成し、`.patch` ファイル1本として `/tmp/cmux-diff-viewer-<uid>/` の内側に書き、そのファイルを指すマニフェストを渡す。**

- diff の生成はアプリ側の責務になる（ディスク側の内容とバッファの内容は既に両方メモリにある。§9.2 の `FilePreviewSaveConflict.diskContent` と `textContent`）
- 生成した `.patch` は **root の内側**に置く。出力先は `NSTemporaryDirectory()` ではない
- マニフェスト生成側（`Native/DiffSidecar`）の契約は本書で未読 `[要調査]`。アプリ側から同形式の JSON を書けるかは未確定-03 で確認する
- **セキュリティ制約は新規-D に必須項目として書く**（root のパーミッション、`.patch` の後始末、24時間保持されるセッションとの整合）

したがって FR-08 は未確定-03 のまま据え置き、**Reload / Keep Mine の2択で先に成立する設計**にしてある（§9.2 で `.compare` だけが未実装）。**ただし2択で先行リリースしてよいかは決まっていない**（02 FR-07 AC1 は3択を求めている。§20.1 / 未確定-03）。

### 10.3 保存衝突の解決

## 11. Persistence（Session Restore への影響と後方互換）

### 11.1 セッションスキーマは変更しない

`SessionFilePreviewPanelSnapshot` は `filePath` のみ、`SessionMarkdownPanelSnapshot` も `filePath` のみ `[実コード: Sources/SessionPersistence.swift:1656-1661]`。`SessionPanelSnapshot` は `PanelType` + 種別ごとの Optional な snapshot を持つ `[実コード: 同 :1689-1719]`。

**本設計はこのスキーマにフィールドを1つも追加しない**（NFR-02 AC3）。理由:

- ハイライト・行番号の有効状態は `UserDefaults`（`fileEditor.*`）に置く。パネルごとの状態ではない
- ハイライト結果・行インデックスは派生データであり、ファイルを読み直せば再構築できる
- 保存衝突の pending 状態は揮発でよい。アプリ再起動時にファイルを読み直せば `isDirty` は false から始まる

結果として **NFR-01 / NFR-02 は「何もしない」ことで満たされる**。これは D-1（新 `PanelType` を作らない）と一体の判断である。

### 11.2 後方互換の確認方法

`SessionWorkspaceSnapshot.panels` は非 Optional の配列で合成 `Codable` `[実コード: 同 :1839]`。新旧どちらの方向でもスキーマが同一なら、旧セッションファイルは無変更でデコードされる。§16 に「実装前に書かれたセッション JSON を実装後のビルドでデコードする」テストを置く。

## 19. 未確定事項（設計段階で新たに判明したもの）

要件定義の未確定-01〜11 のうち **未確定-01 は §5 D-1 で解消**した（Panel 層に足す）。以下は本書の設計作業で新たに判明したもの、または要件定義の未確定を具体化したもの。

### 新規-A `applyTheme` の `textColor` 一括代入をどう扱うか（実装直前の確認事項）

`FilePreviewTextEditor.applyTheme` は `updateNSView` から毎回呼ばれ、`textView.textColor` にテーマ色を代入する `[実コード: Sources/Panels/FilePreviewTextEditor.swift:61-66, 109]`。§7.4 では `preservesTextColor` フラグを足す案を採ったが、これは既存の static メソッドのシグネチャを変える。呼び出しは同ファイル内2箇所だけなので影響は閉じるが、upstream が同メソッドを触っていた場合コンフリクトする。

**選択肢**: (a) 引数を足す、(b) ハイライト適用後に毎回 `applyTheme` の副作用を打ち消す（無駄な再描画が入る）、(c) `applyTheme` を呼ぶ前にハイライト有効かを判定して呼び分ける。本書は (a) を仮採用した `[設計判断]`。

### 新規-B 属性のみの変更が Undo に乗らないことの確認

§7.3 の前提（`textStorage` への属性追加は `NSTextView` の Undo に登録されない）は AppKit の挙動に依存し、実コードで確認していない `[設計判断]`。実装の最初のステップでこれを確認するテストを書き、成り立たなければ設計を見直す（`textView.shouldChangeText` を通さない別経路、または `undoManager.disableUndoRegistration()` で囲う）。

### 新規-C `FilePreviewLineIndex` の増分更新をどこで受けるか

`NSTextStorage` の編集通知（`didProcessEditing` / `NSTextStorageDelegate`）を使うか、`Coordinator.textDidChange` `[実コード: Sources/Panels/FilePreviewTextEditor.swift:124-128]` で全再構築するかが未決。前者は `editedRange` / `changeInLength` が取れて効率がよいが、`SavingTextView` に delegate を1つ足すことになる（§7.1 で「フィールドを追加しない」と決めた方針と緊張する）。後者は大きなファイルで毎キーストローク O(N) になる。加えて **§8.3 の保留シフト方式は `editedRange` / `changeInLength` が取れることを前提にしている**ため、後者を採るなら §8.3 の増分更新そのものが成立せず、全再構築の debounce に切り替える必要がある。`[設計判断]` としては前者だが、実装時に再評価する。

### 新規-D Compare は `/tmp/cmux-diff-viewer-<uid>/` への `.patch` 書き出しを伴う

§9.4 のとおり、既存 Diff Viewer が受け取れるのは **trusted root の内側にある `.html` / `.js`,`.mjs` / `.patch` だけ**である `[実コード: Packages/macOS/CmuxBrowser/Sources/CmuxBrowser/DiffViewer/CmuxDiffViewerSessionPreparer.swift:291-306, :89-92, :225-227]`。したがって Compare の実現形は「アプリ側で unified diff を生成し、`.patch` として `/tmp/cmux-diff-viewer-<uid>/` `[実コード: 同 :18-22]` の内側に書く」ことに限られる。

決める必要があるのは (a) `.patch` の書き出しとライフサイクル、(b) マニフェスト生成側 `Native/DiffSidecar` の契約 `[要調査]`、(c) 下記のセキュリティ制約、である。**要件定義の未確定-03 に (a)(b)(c) を追加する。**

**(c) セキュリティ制約（Compare を実装する場合の必須要件）**

書き出す `.patch` には、**ディスク側の内容と未保存バッファの内容の両方が平文で載る**（「一時ファイルが残る」という程度の話ではない）。次を必須制約として満たさない限り Compare を実装しない。

1. **root を `0700`、`.patch` を `0600` で作る。** Diff Viewer 側の trusted root 検証は `lstat` で「ディレクトリであること」と「uid が自分であること」しか見ておらず、**ディレクトリの mode を検証していない** `[実コード: 同 :215-222]`。`/tmp` は他ユーザーが traverse 可能なので、root が `0755` で作られていれば同一マシンの他ユーザーから未保存内容が読める
2. **Compare セッションの終了時に確実に unlink する。** 終了とは「パネルの close」「衝突の解決（Reload / Keep Mine）」「アプリ終了」の3つすべてを指す
3. **24時間保持との整合を明示する。** URL スキームハンドラ側のセッション寿命は `maxSessionAge = 24 * 60 * 60` 秒 `[実コード: Sources/Panels/CmuxDiffViewerURLSchemeHandler.swift:33]` であり、ファイルを消してもセッション登録はしばらく残る。ファイル削除とセッション失効のどちらが先でも壊れないことを確認する

### 新規-E `OpenConfiguration.arguments` を併用するか、`preferredEditor` 経路に限定するか

**訂正**: 「LaunchServices 経路には引数を渡す口が構造的に無い」は**誤り**である。`NSWorkspace.OpenConfiguration` には `arguments: [String]` がある `[実コード: MacOSX26.0.sdk/System/Library/Frameworks/AppKit.framework/Headers/NSWorkspace.h:181-185]`。ただし同ヘッダが「**新しいアプリインスタンスが作られるときに渡す引数**」と定めており、サンドボックス下では無視される。cmux は非サンドボックスなので後者は満たすが、既存実装は `configuration.createsNewApplicationInstance = false` を明示しており `[実コード: Sources/Panels/FilePreviewPanel.swift:116]`、**エディタが既に起動していれば引数は無視される**。

したがって問いは **「不確実な `OpenConfiguration.arguments` を併用するか、`preferredEditor` 経路に限定するか」** である。本書は後者を仮採用した（§10.2）。前者を採る場合、「起動済みなら行に飛ばない」という不安定な挙動を FR-09 AC2 の答えとしてよいかを決める必要がある。

`preferredEditor` 経路に限定する場合、`app.preferredEditor` の値にプレースホルダ（`{file}` / `{line}`）を導入するか、既知コマンド名から形式（`code --goto <file>:<line>` / `xed --line <n> <file>`）を推定するかがさらに未決 `[要調査]`。

**プレースホルダを導入する場合の必須制約（シェルインジェクション対策）**

既存実装はパスを必ずシェルクォートしている: `process.arguments = ["-c", "\(command) \(url.path.posixShellSingleQuoted)"]` `[実コード: Packages/macOS/CmuxWorkspaces/Sources/CmuxWorkspaces/FileOpen/PreferredEditorService.swift:74]`。`{file}` を素朴に文字列置換するとこの安全策が失われ、`'` を含むファイル名で `/bin/sh -c` へのコマンドインジェクションが成立する。

1. **`{file}` は置換後も必ず `posixShellSingleQuoted` を通した文字列にする**（置換値をクォート済みの文字列にする、が正）
2. **`{line}` は `Int` に限定し、文字列を受け付けない**（`Int` を `String(describing:)` した値だけを埋める）
3. 上記2点を `FilePreviewExternalOpenLocationTests`（§16.2）で固定する

### 新規-F Settings 行の置き場所は「App セクション」である

`fileEditor.*` は専用セクションを持たず、`AppSection.swift` の Markdown Viewer Font と iMessage Mode の間にレンダリングされている `[実コード: Packages/macOS/CmuxSettingsUI/Sources/CmuxSettingsUI/Sections/AppSection.swift:503-514]`。ハイライトと行番号を「File Editor」という独立セクションに分けるかは未決。分ける場合、`CmuxSettingsUI` への差分が大きくなり NFR-08 に不利。**本書は既存どおり App セクションへ追加する前提で書いた** `[設計判断]`。

### 新規-G FR-09 のために「下位パッケージの public API 追加」と「ヘッダメニューの経路追加」を許容するか

FR-09（外部エディタへの行番号）を成立させるには、独立した2つの許可が要る。どちらも本書では決められない。

1. **下位パッケージ `CmuxWorkspaces` の public API を1メソッド増やしてよいか。** `PreferredEditorService` は `public struct` `[実コード: Packages/macOS/CmuxWorkspaces/Sources/CmuxWorkspaces/FileOpen/PreferredEditorService.swift:27]` で、app target の型を引数に取れない。`open(_ url: URL, line: Int?)` を足す形になる（`FileOpening` プロトコル `[実コード: 同ディレクトリ/FileOpening.swift:9-12]` は変更しない）。P-5 のはみ出しであり §18.4 に記録済み

どちらも「否」であれば FR-09 は実装できない。その場合は FR-09 を MVP から外す判断になる。

### 20.2 技術的実現性

- 最大のリスクは **ハイライトエンジンが「全文を読みつつ指定範囲だけを返す」を安く実行できるか**（§5 D-2 の performance 軸）。§6 の seam は全文 + 全文座標の `range` を渡す契約なので**正しさは担保される**が、エンジンが `range` を無視して全文を色付けする実装（Highlightr / highlight.js 系）では計算量が減らない。スライスを渡す回避策はブロックコメント・複数行文字列が境界で壊れるため採らない（§7.3）
- 次のリスクは **`FilePreviewLineIndex` の増分更新**（新規-C）。全再構築に倒せば正しいが遅い。テストで全再構築との一致を保証する設計にした
- `NSRulerView` はリポジトリに先例がなく `[設計判断]` の比重が高い。ただし AppKit の標準機能であり、失敗しても代替案（§5 D-3 の2番目）に退避できる

### 20.3 拡張性

- `FilePreviewSyntaxHighlighting` の seam により、エンジンを差し替えても `FilePreviewSyntaxHighlightController` 以降は不変（§5 D-2）
- `FilePreviewTokenRole` を意味論で切ったことで、テーマ追加はパレット1枚の追加で済む（FR-11）
- `FilePreviewLineIndex` は行番号以外（将来の折りたたみ）にも使える。ただし **FR-09 のカーソル行はこれに依存させない**（行番号設定オフのときインデックスを構築しないため。§10.2 / §20.8）
- 一方、**LSP（REQ-25）や Live Diff（REQ-24）への橋渡しは意図的に設けていない**。MVP 対象外であり、投機的な抽象化は入れない

### 20.4 運用性（upstream 追従とデバッグ容易性）

- §18 で差分の局所化状況を明示。新規16ファイルは upstream と衝突しえない。はみ出し分と理由は §18.4

### 20.5 セキュリティ（ファイルアクセス権限とサンドボックス）

- アプリはサンドボックス化されていない（`com.apple.security.app-sandbox` はどの entitlements にも存在しない）。したがってファイルアクセスに新しい権限要求は発生しない
- 配布ビルドは `allow-jit` / `allow-unsigned-executable-memory` / `disable-library-validation` を持つ `[実コード: cmux.entitlements:5-10]`。Highlightr（JavaScriptCore）を入れても新しい entitlement は不要
- **注意点（訂正）**: ハイライトを highlight.js 系に倒すと、ファイル内容を JavaScriptCore に渡すことになる。ただし **highlight.js は「新たに持ち込む第三者コード」ではない** — macOS 本体は既に `Resources/markdown-viewer/highlight.min.js` を同梱して Markdown プレビューで実行している `[実コード: Resources/markdown-viewer/highlight.min.js, Sources/Panels/MarkdownPanelView.swift:7]`。したがってリスクの実体は「新しい第三者コードの追加」ではなく **「エディタで開いた任意のファイルの内容を、これまで Markdown 本文しか通していなかったエンジンに通す」という入力面の拡大**である。ローカル完結でネットワークには出ない。エンジンを自前実装に倒せばこの面は消える（未確定-02 の評価軸に「エンジンにどの範囲のファイル内容を渡すことになるか」を含める）
- **新規-D（Compare）は明確なセキュリティ論点**である。書き出す `.patch` には**ディスク側の内容と未保存バッファの内容の両方が平文で載る**。置き場所は他ユーザーが traverse 可能な `/tmp` の下であり、Diff Viewer 側の root 検証はディレクトリの mode を見ていない `[実コード: Packages/macOS/CmuxBrowser/Sources/CmuxBrowser/DiffViewer/CmuxDiffViewerSessionPreparer.swift:215-222]`。新規-D の必須制約（root `0700` / ファイル `0600` / 確実な unlink / 24h セッションとの整合）を満たさない限り Compare を実装しない
- 保存衝突 UI は既存の保存経路（`FilePreviewTextSaver.save` `[実コード: Sources/Panels/FilePreviewPanel.swift:959-971]`）を変えないため、書き込み権限まわりの挙動は不変

### 20.8 運用リスク（リソース蓄積・大容量ファイル・フォールバック）

| リスク | 緩和 |
|---|---|
| ハイライト用 `actor` の engine がパネルを閉じても残る | コントローラをパネルのライフサイクルに紐付け、`close()` 相当で破棄。`MarkdownPanel.close()` `[実コード: Sources/Panels/MarkdownPanel.swift:245-255]` / `FilePreviewPanel` の `isClosed` `[実コード: Sources/Panels/FilePreviewPanel.swift:1003]` の既存パターンに合わせる |
| デバウンスタスクが積み上がる | 新しい編集ごとに前の `Task` を `cancel()`。世代番号で結果を破棄 |
| **スクロール購読 `Task` がパネルを閉じても生き続ける** | `for await` ループは自身を強参照するため、`attach` で作った購読 `Task` を保持し `detach()` で必ず `cancel()` する。ループ内は `[weak self]` で受けて nil なら `break`。これが無いと `deinit` が呼ばれず `NSTextView` / `NSScrollView` ごとリークする（§7.3）。§16.2 に「`detach()` 後に購読タスクが終了する」ケースを置く |
| **アプリ内の全ビューの bounds 変更で発火する** | `notifications(named: NSView.boundsDidChangeNotification, object: clipView)` と `object:` を必ず指定する（§7.3）。省くとターミナルを含む全 `NSView` の bounds 変更で再計算が走り、§7.7 の非影響が破れる |
| `FilePreviewLineIndex` のメモリ（16 MB ファイルで約 4 MB の `[Int]`） | 許容と判断（§8.3）。行番号設定オフのときはインデックスを構築しない。**FR-09 のカーソル行はこのインデックスに依存させない**ため、設定オフでも FR-09 は劣化しない（§10.2） |
| 大容量ファイルでの初回描画遅延 | 可視範囲のみ処理。閾値超過はハイライトごとスキップ（FR-03） |
| エンジンが例外・タイムアウトで結果を返さない | `runs(for:)` は `[FilePreviewHighlightRun]` を返す（`throws` にしない）。空配列 = プレーン表示にフォールバックし、テキストは常に表示される（FR-02 AC2 と同じ状態へ落ちる） |
| ハイライトが色を壊した状態で残る | 設定オフに切り替えると `invalidateAll()` → `removeAttribute(.foregroundColor)` → `applyTheme` の従来経路に戻る。ユーザーが自力で回復できる |
| 衝突バナーが出たままファイルが消えた | `isFileUnavailable` の分岐は `content(previewRevision:)` の**内側**にある `[実コード: Sources/Panels/FilePreviewPanel.swift:1448-1449]` 一方、バナーは `content` の**兄弟**として `VStack` 直下に置く（§9.3）。したがってバナーは自動では消えない。**表示条件に `!panel.isFileUnavailable` を含める**ことで消す（§9.3）。`isFileUnavailable` は dirty 枝でも更新され続けるので `[実コード: 同 :1290]`、ファイルが消えれば `.unavailable` 経路で立つ `[実コード: 同 :1275-1284]` |
